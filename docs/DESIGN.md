# Design

Layered: read **1** to get it; go deeper only if you need to.

## 1. Principles (the whole design in five lines)
1. **Claude Code is the runtime.** We never rebuild what it ships (subagents, worktrees, `claude -p`/`--bg`, hooks, cross-session messaging, Remote Control, auto-memory). Our code is thin glue and shrinks as the platform grows.
2. **Deterministic bookkeeping = scripts; thinking = Claude.** Worktrees, commits, pushes, PRs, board, notifications, restarts are scripts that never drift or cost tokens. No always-on "manager agent."
3. **Isolation by construction.** One task = one git worktree + branch (can't overwrite each other). Untrusted/autonomous = Docker container (`ccbox`).
4. **Durable artifacts, ephemeral context.** State lives in files (journal, board, git, PRs), not in a context window. Workers are fresh per iteration; long sessions hand off to a journal and restart clean.
5. **Human gates are permanent and mechanical.** Merge to default branch, spend, external comms, destructive/host ops are blocked by a hook for autonomous and member-facing sessions, and need the owner.

What a session actually *does* with all this between tasks — pick up work, journal, hand off, close an ask — is `docs/WORKING.md`; this file is why the pieces are shaped the way they are.

## 2. Architecture (one screen)
| Layer | What | How |
|---|---|---|
| Access | laptop/phone reach the box | Tailscale SSH (primary), a Cloudflare tunnel (backup), a rescue cable on a static address, Claude app via Remote Control |
| Persistence | work survives disconnects/reboots | tmux `main` (user service at boot) hosts every session; `cc` puts sessions in it |
| Sessions | one Claude per unit of work | `cc <repo>` planning session (primary worktree) · `cc <repo> <track>` worker session (own worktree/branch) |
| Autonomy | hands-off execution | `cc … --go "task"` → `cc-loop`: headless `claude -p`, fresh context per iteration, journal-driven, capped by `--max-budget-usd`/turns, ends in a PR |
| Coordination | who is doing what | `cc-board` sidecar JSON per repo (never in git) records status; **`cc-reconcile` is the one decider** of what a track's state actually is, and writes a snapshot everything downstream (`cc ls`, `cc digest`, the Home tab) reads instead of re-deriving it |
| Safety net | nothing lost, nothing dangerous | Stop hook `cc-checkpoint` (auto-commit+push in track worktrees only) · PreToolUse hook `cc-guard` (gates, for autonomous *and* member-facing sessions) |
| Human loop | box reaches the owner; owner checks in | `cc-notify` → Slack + ntfy push; `cc-msg`/`--say` types into a running session; `cc-handoff` owns the handoff in **two paths** — the successor starts *alongside* its predecessor (`--overlap`) or the old stop-then-restart (`--replace`), which the overlap fails into; `cc-slack` routes `#<repo>` to that repo's live session over one Socket-Mode daemon |
| Sandbox | unrestricted Claude, contained | `ccbox <name>`: Docker with four mounts and nothing else — `~/dev/<name>` → `/workspace/<name>`, volume `ccbox-claude` (login), volume `ccbox-hist-<name>`, `~/ccbox/allowed-domains` read-only; NET_ADMIN egress allowlist, IPv6 off, memory/pids capped, `--dangerously-skip-permissions` inside only |

## 3. Components (2–3 lines each)
- **cc** — the front door. Repo → planning session; repo+track → worktree session; `--go/--say`; `resume` menu; `done` → PR; `rm`; `handoff`. Names are validated (no paths, no option lookalikes), window creation is `flock`ed, roles are injected with `--append-system-prompt`, and deterministic session IDs on the board make resume exact.
- **cc-loop** — the ralph loop. Prompt = task.md + tail of progress.md. Stops on `STATUS: DONE` (→ PR + notify), `STATUS: BLOCKED: q` (→ notify owner), 2 errors, 2 stalled iterations, max-iter, or two capped iterations that produced nothing — a cap that still produced work is not a failure. Exit codes are meaningful (0/3/4/5/6/7) and every non-zero one leaves the board `blocked`, never `running`.
- **cc-checkpoint** — Stop hook. No-op unless cwd has a `.cc/track` marker; refuses when HEAD is not that track's branch or when staged names look like secrets (`.env*`, `*.pem/key`, `credentials*`) → reason in `.cc/checkpoint.err`. Push failures are never fatal but never silent: stderr to `.cc/push.err`, which `cc ls`/`cc digest` flag as `push!`.
- **cc-owed** — Stop hook, same payload as `cc-context` and carried through it (`--with`, one decision, the debt first). Reads the session's own transcript for the newest event in every Slack thread it touched: their message with no word of ours after it is a debt, our own question posted without `needs_owner` is the other. cc-slack's `flags.json`/`marks.json` cancel one (🏁 closed · ✅ done · ❓ already declared); they are read, never recomputed. Said once per debt, on a ledger (`~/.cc/state/owed/owed.jsonl`).
- **cc-guard** — PreToolUse hook, active for `CC_ROLE=worker|member` or a `.cc/track` / `.cc/member-facing` marker above the cwd. The marker is the truth and can only *tighten*; the env var is a convenience. Denies merge/deploy, push to default/force, external GitHub comms & email, sudo/host/network/service changes, destructive git/docker, recursive deletes and edits outside the worktree (path resolved first, so `../` cannot walk out), ref/HEAD rewrites. A missing `jq` fails closed. **role=member** adds: no dispatching work (`cc … --go`, `cc-loop`, headless `claude -p`), no reading the box's secrets (`~/.cc/config`, `~/.ssh`, `~/.claude/settings.json` — through Bash *and* the file tools), no re-wiring Slack, no writing another session's `~/.cc/state`; `cc-notify` stays allowed, because that is how it escalates.
- **cc-board** — Python, file-locked JSON at `~/.cc/boards/<repo>.json`: tracks, status, notes, PR, session id. `cc board show|add|note|status|json`. It is an **index, not a brief**: what a track was actually asked to do lives in its `task.md`, and its running detail in `progress.md`, because a worker reads those and nothing reads a paragraph stuffed into the JSON. The board says *that* a track exists and where it got to; it never carries the instructions.
- **cc-reconcile** — the board against the box, on a timer (20 min, and 5 min after boot). It sorts drift into two kinds and the sorting is the whole job: **decidable** has one right answer in the evidence (the PR merged, so the track is merged) and is applied through `cc-board`; **undecidable** needs a person (a PR closed unmerged, a worktree gone, work that never committed) and is reported, never guessed. It writes a track's status and a note saying it did — it deletes, opens and merges nothing. *Alive* is the fact no file holds: a `claude` in the track's worktree, a `cc-loop` above it, or a live pane in its window — and `waiting` is not its opposite, because a worker's own `STATUS: BLOCKED:` line outranks presence and is what reaches the owner. **It is the sole decider**: every unfiltered run writes `~/.cc/state/reconcile.json` — effective state, live presence, who each track waits on and why — and `cc ls`, `cc digest` and the Home tab read that rather than each re-deriving it. It also carries the sweeps that need a timer rather than a session: `cc-handoff --sweep` and pruning dead `cc-trust` entries, both because a crashed session no longer has the Stop hook that would finish its own work.
- **cc-handoff** — owns the whole handoff lifecycle: every phase decision, both paths, the deadline and the sweep. `cc handoff` is just the spelling — it delegates here, as does `cc-context`, which only ever *measures* and emits one `--event`. That consolidation is the point: the sequence used to be split across three files, and that split is what let a survivor's un-gate depend on a marker nobody swept. The invariant is one record file naming the **live** session — the live one owns the channel and may act, the other is muted and gated (`cc-guard` reads the same record) — and cutover is a single atomic `os.replace()` of it. Ownership only moves forward on an explicit successful act, so every failure lands on "the predecessor is still in charge"; a missing or corrupt record means exactly that. Bounded by a deadline the predecessor's own Stop hook watches, so there is no new timer and no new daemon, and the overlap path fails *into* the old stop-then-restart rather than taking it down.
- **cc-audit** — recurring hands-off review, read-only by construction. `cc-audit auto` (03:30 UTC daily) picks by date: day 1 monthly · day 8 arch · day 15 delete · Sunday weekly · every 3rd day-of-year review · otherwise **the gates alone** — a quiet day is quiet to the owner, not blind to a red default branch. It owns exactly one piece of state, the **`main-gate` board row**: the first red suite becomes one track that updates in place and closes itself on green, so a session learns main is broken *before* it dispatches instead of every track rediscovering it. The LLM passes get evidence collected for them into a run directory and a tool set with no shell and no MCP; the codex second opinion is walled differently and more weakly (`--sandbox read-only`: a shell exists, but caged and offline), and the two must not be described as the same wall. Bounded by silence, never by elapsed time — a review still emitting after three hours is working.
- **cc-config** — the one reader and writer of `~/.cc/config` (`get|set|unset|list`), so that file has one parser and one precedence rule: the environment wins over it, a variable that is SET wins even when EMPTY, writes are `flock`ed and land mode 600. It is never *sourced*, anywhere — it holds the box's tokens, so an executed config is both a shell injection and a way to hand every secret to the next child; two of the four tools this replaced did exactly that.
- **cc-notify / cc-msg / cc-digest** — owner push (ntfy topic in `~/.cc/config`), keyboard-injection into a session (tmux), status digest (+ `cc-digest.timer` daily 13:00 UTC). The Slack half routes by title (`#<repo>`, else `#alerts`) — except an **escalation**, which is *delivered*: `--owner`, or any session under a `.cc/member-facing` marker, DMs the owner (unpaired: `#alerts`). A channel session that routed its escalation by title would post it where the members are and nowhere near the one person it is for.
- **cc-slack** — two roles in one file. `cc-slack daemon` (unit `cc-slackd`) is the box's only Slack connection — Socket Mode delivers each event to a single socket, so one daemon, no inbound port — plus a local router on a Unix socket. `cc-slack channel` is the stdio MCP *channel* server every session spawns; it takes its target from the cwd, pushes `<channel>` events into the session and exposes `reply`/`react`/`file`. Details that are decisions, not plumbing, are in §4.
- **cc-publish** — the generic half publishes itself. Once the default branch has moved, the whole `core/` prefix of `origin/<default branch>` goes to its own public repo as one commit parented on that repo's tip: no path filtering, no rewriting, no cherry-picking. **A timer, not an event** (`cc-publish.timer`, 15 min): every run is idempotent, so nothing has to notice the merge and a merge from anywhere — a session, the web, another machine — publishes alike; nothing on the 👍 path calls it any more, because nothing there knows when the merge happened — the timer is the path, and the daemon's hourly tick is the only fast one left. Its one veto is the **identity gate** (contents, file names and the commit subject vs this box's user, host and control-repo names, plus `PUBLISH_DENY`); a hit aborts loudly having pushed nothing (stderr + `cc-notify` + `~/.cc/state/publish.log`), and on a timer pages the owner once per distinct reason, not every 15 min. Unconfigured (`PUBLISH_REMOTE` unset) it is a no-op.
- **cc-land** — the box's only merger, and the owner of the deploy that follows. Gates first, against the PR's OWN head in a throwaway worktree (the default branch does not contain the change, so gating it there would be a green light for code nobody ran), then the squash merge, the `#approvals` card, the board, the ask ledger, `install.sh`, the units the change *added*, the restarts, and last the ask's own delivery check. **A 👍 does none of that itself**: it writes one job to `~/.cc/state/land/<repo>-<pr>.json` and starts a transient `systemd-run --user` worker. That shape is the point — the deploy restarts the daemon that took the 👍, so anything running inside it dies half-way through its own install. The file name is the idempotency key, one `flock` admits one worker, and every durable write happens *before* the thing it describes, so a kill or a reboot at any point converges to at most one merge and exactly one message to the owner. `<repo>.applied` records the SHA `install.sh` last ran on — the only thing that can notice a merge made in GitHub's own UI and deploy it. It fails **closed**: a queue it cannot write or a worker that will not start is said in the channel, and nothing merges. Deploy steps are retried three times (they fail on the state of the box); a red gate and a refused merge are verdicts, and want a person.
- **ccbox** — reference-devcontainer image (node:22). `init-firewall.sh` — the only `sudo` the box user has — resolves `ccbox/allowed-domains` + GitHub's meta ranges into an ipset, allows DNS only to the container's resolvers, and is re-runnable. Login shared via volume `ccbox-claude`, workspace per project, tokens via `ccbox/env` (never `~/.ssh`); refuses to sandbox the control repo it lives in.
- **cc-units / cc-settings — one declaration each of what must be installed, and something that checks it is.** `config/units.json` is the ONE list of core user units (link · enable · start · health · restart); `install.sh` links and enables from it, `cc-audit` health-checks from it, static checks fail when it and `config/systemd-user/` disagree. It replaced three hardcoded lists in two files that had already drifted — three timers the installer enabled were invisible to the audit. `restart` is per unit because a landing cannot infer it: a changed `.timer` needs a **restart and a re-arm** (`daemon-reload` alone leaves a new `OnCalendar` at `Trigger: n/a` — a daily job silently off, 2026-08-31), a `.service` needs a restart, and `tmux-main` — which owns the tmux server every session lives in — is never restarted automatically, only recorded as the owner's action. `config/claude-managed.json` is the same idea for `~/.claude/settings.json`: the three hook registrations the mechanical gates are made of, plus the deny rules, and **nothing else** — a theme change is not drift. **Nothing automatic writes that file.** It holds `permissions`, and a hook entry runs a command on every prompt, so `cc-guard` keeps it a secret path; install and audit only ever *report*, naming the unapplied entries rather than counting differing lines (27 of them, ignored for days, hiding a gate that captured nothing). `cc-settings apply` is the owner's own hand: it refuses inside a session, without a terminal, and in a track worktree, and proves `permissions` came through byte-identical before it swaps the file.
- **Boot** — `tmux-main.service` (linger) runs `tmux new-session -d -s main -n box … cc-rc` itself, so the server is born in that unit's cgroup. `cc-rc` waits for internet, runs a Remote-Control Claude named after the box (`$CC_BOX`), and respawns with backoff. `cc-boot` is `cc`'s idempotent helper: no-op if `main` exists, never a `restart` of a live server (ExecStop is `tmux kill-server`). `cc-heartbeat` + `cc-boot-notify` date and announce every power cut.

## 4. Decisions and what we deliberately did not build
- **No fleet, no always-on overseer.** Research (Anthropic's multi-agent writeup; Cognition's "Don't build multi-agents"; METR half-life data) says coding rewards one strong linear agent with fresh context per chunk. Parallelism = 2–4 independent worktrees, not 20. An always-on coordinator burns tokens and rots its own context; everything it would do mechanically is a script.
- **No custom message bus.** Claude Code has native cross-session messaging (`SendMessage`, push-based, zero idle cost) and Remote Control. We added only what does not exist natively: owner notification (Slack/ntfy) and a deterministic waker (`cc-msg`). A read-only MCP for Claude.ai check-ins was retired 2026-08-27 once Slack covered the same need with one fewer public surface; the code stays parked in the private overlay.
- **Slack via native channels, not a bot framework or Claude Tag.** Claude Tag runs cloud sessions and cannot reach this box; a Bolt bot with `claude -p` per message would rebuild sessions. Channels deliver into the session that already exists — the same one in tmux and Remote Control. Cost: a research preview, so sessions carry `--dangerously-load-development-channels server:cc-slack` and the flag may change.
- **Slack channel membership is the access control.** Anyone who can post in a routed channel is heard and delivered identically (`role="member"` in the tag) — which is why what the box creates is private by default and a sub-channel inherits its parent's humans. **A reaction is a verdict, and anyone in the channel gives it** (owner's decision, 2026-08-30): a member's `:+1:` in `#approvals` enqueues the landing job that gates, merges and deploys, their 🏁 closes a thread, and any other reaction reaches the session with `user=` and `role=`, so it can weigh a colleague's 👍 against the owner's. **A verdict settles the thread in both directions**: our reaction on their message and *the owner's* on ours both file it 🟠 and disarm the 30 min stall, because a thread they have already answered must never come back as ❓ (their complaint, 2026-08-30). Only 👀 ("received") and the bookkeeping marks settle nothing, and only the OWNER's reaction closes a thread that waits on the owner. Membership of a channel the owner curates *is* the approval gate, and sensitive channels have no members. Owner-only: DMs, permission answers (`yes <id>` authorizes, it does not judge), `!` commands beyond `!help`/`!status`, `@alias` hand-offs, status marks and App Home. Asked by a member for something gated, a session does the ungated part, says which part is not, and @-mentions the owner.
- **Every outbound post is rewritten once** (`linkify_mentions`): `@handle` becomes a real `<@U…>`, resolved against the members of the channel being posted to before the workspace-wide table, so one Ada in the channel resolves even when three exist elsewhere. Handles, display and real names and first tokens all index. `@main`/`@<alias>`, `@here`/`@channel`, code spans and anything ambiguous are left as typed — a wrong id pings the wrong human — and logged, so an escalation that reached nobody leaves a trace. Inbound `<@U…>` renders as a handle, so what a session reads is what it can write back.
- **A session may attach a file to its own thread**, bounded because it moves bytes off the box: the path is resolved through symlinks and accepted only under the session's cwd, `/tmp` or `~/.cc/slack/files`, ≤25 MB, no directories; with no token it lands in the outbox and the tool *says* it was not sent.
- **`cc-board` vs native agent-teams.** Agent teams (experimental) overlap the board. We keep the board (simple, stable) and will drop it when the native feature is GA.
- **`--go` (headless, capped) only.** `--bg` is not wired into `cc`: `--go` is deterministic, budget-capped and journal-driven, and one worker mode is easier to reason about than two.
- **Context strategy = both.** Ephemeral workers (loop) and restart-rehydrate (`cc handoff`) share the same journal, so nothing is decided up front.
- **A handoff is decided on the measured context, never on a hunch** — too early throws away a good session, too late and auto-compaction has already dropped the detail. `cc-context` reads the number off the session's own transcript (last assistant turn's `usage`, or the `compact_boundary` after it), and the Stop hook records one per turn because the hook payload is the only place the transcript path is handed over. The honest part is the *window*: the transcript's model string has the `[1m]` suffix stripped, so 200k and 1M look alike — the window comes from evidence (the session's own compaction, `cost-state`, the live process's `--model`) and when there is none the output says the percentage is an assumption. `--over` refuses to act when it cannot measure. **Three lines, each a percentage with a floor under it** (`CC_CONTEXT_WARN_PCT` 30 / `CC_CONTEXT_HANDOFF_PCT` 40 / `CC_CONTEXT_CEILING_PCT` 60, floors 60k and 90k — 300k / 400k / 600k on the 1M window here): journal, hand off, hand off regardless. They are early on purpose — this is about how sharp a session is, not about running out of room, and the evidence says there is no plateau to sit below (Chroma's *Context Rot* degrades at every length tested; NoLiMa has 10 of 12 long-context models under half their short-context score by 32k). **Why both a percentage and a floor:** degradation tracks absolute tokens more than the fraction used, so a small window buys no extra good tokens — but a bare percentage of one lands under what a session needs to work at all (30% of 128k is 38k, mostly prompt and tools). **The handoff is pending, not immediate:** crossing 40% restarts nothing; the restart happens at the first turn with nothing in flight — no background or scheduled task, no unfinished merge/rebase, nothing uncommitted or unpushed in any worktree of the repo — because mid-task state lives in no file and a wrong "idle" reading is a handoff in the middle of something. `in_flight` is pessimistic by design: anything git cannot answer counts as busy. The 60% ceiling goes anyway. A session with no live window (a headless worker) is never restarted from here — its loop already gives it a fresh context — so it is told to journal instead. The message is delivered through the Stop hook's own `decision: block` channel, said once per line, never while another Stop hook holds the session, and only to a session that has a journal. **Every crossing is on a durable ledger** (`~/.cc/state/context/handoffs.jsonl`: when, session, repo/track, percentage, tokens, which line): a count nobody can compute is a number that will be wrong wherever it is shown.
- **What a session owes is measured, not remembered.** Forgetting to answer in Slack, and asking a question without labelling it, were both fixed with prompt sentences that kept being forgotten — a session that forgets cannot notice that it forgot. So the box checks it in the one place it already checks how full a context is, and says it once, mechanically (`cc-owed`). The rule that a ❓ is the *sender's* to declare is not weakened by it: nothing is inferred from prose into a mark, the hook only asks the session that wrote the words whether it is actually waiting on an answer.
- **A member-facing session is marked, not instructed.** `.cc/member-facing` in a folder makes every session started there role=member: `cc` exports `CC_ROLE=member` and adds one sentence to the prompt, but the gate is the marker — `cc-guard` walks up from the cwd, so it holds for subagents, for a session started by hand, and with no env at all. Only the owner lifts one, per call. **The honest ceiling:** the command gates are a *blocklist*, not a sandbox — they stop accidents and casual prompt-injection, not a determined attacker (a redirection, a copied binary, a script written first). Real containment is `ccbox`.
- **A channel is a session; no channel is a dead end.** One that maps to no project *becomes* one on its **first message**, never in advance: `~/dev/<channel name>` (lower-cased, folded to `[a-z0-9-]`) with a `CLAUDE.md` from `templates/channel-CLAUDE.md`, the marker `.cc/member-facing` and `git init`, then the ordinary autostart delivers the message. **Member-facing by default is the point:** a channel anybody can create must not yield an ungated session. Bounded at 3 new dirs an hour (`~/.cc/slack/provisioned.json`) — the cap is on creation, an existing dir is reused forever. Never for DMs, `#approvals`/`#alerts`, a sub-orch channel, or a name that normalises to nothing. A `#<repo>--<track>` channel whose window is a headless worker is never restarted and never left silent: the question goes to the `<repo>` session prefixed `[asked in #<repo>--<track> while its headless worker runs]`. Promoting one to a real project stays the owner's move.
- **The App Home tab is a hierarchy, not a dump.** `home_blocks(st)` is a pure state→blocks function, so the whole layout is asserted on fixtures — busy / quiet / degraded / overflow — rather than eyeballed, the busy one pinned by equality against the design handoff's reference JSON — which is AMENDED in place, with a note naming the superseded spec lines and the owner instruction that superseded them, whenever the owner changes the tab. A spec edited on purpose stays a spec; one quietly stopped being asserted does not. The order answers the owner's two questions in order: header → **RUNNING · BLOCKED · QUEUED** (a downed unit and a usage limit sort above them: the owner must not scroll to learn the box is impaired; nothing running is a *sentence*, never a gap) → **NEEDS YOU** → up to three buttons → a divider, below which everything is secondary by contract: the WHOLE backlog, three board-view buttons, EVERY channel the box knows of (busy families first, quiet ones after — a parent and its sub-channels rank as one family so an indented row is never orphaned), then load, the day's handoff count and audit and units+boot as grey context. Phone first: one line per item, ~40 rendered characters, no two-column `fields` anywhere. Nothing renders a label with nothing under it. Budget ≤18 blocks; `home_cut` drops in the owner's order — boot, handoffs, audit, channels, backlog, board views — and never what is running or needs them.
- **A needs-you row carries the ask, not a count.** `❓ *#repo* · 12m · pick a branch name` — where, how long it waited, and the thing the owner can answer without opening anything. It comes out of the snapshot `reconcile_reactions` already holds, so the dashboard makes no Slack read of its own and there is still exactly one writer per mark. The band merges threads, PRs owed a 👍 and blocked tracks, caps at four lines, and is *absent* — never present-and-empty — when nothing needs them.
- **NEEDS YOU is never wrong: the sender decides, and it clears itself.** Every row is a fact the box *has*, never one it inferred — a thread because the session that posted passed `needs_owner`, a PR because `gh` said OPEN and unreviewed, a track because its journal's newest word is still `STATUS: BLOCKED`. The box only reads a ❓ out of text for the two forms it emits itself (a 🔐 prompt, a `STATUS: BLOCKED` line). Reading it out of prose — a trailing `?`, the words "needs you" — is what put three things on the owner's tab that none of them had to act on (2026-08-30), and a row they cannot act on costs more than one left out. Nothing is ever retracted, either: a declaration is anchored to the moment it was made, so their answer, the session's own next word, an approval on the PR or a `STATUS: DONE` in the journal is already newer than it and the row goes by itself.
- **One vocabulary, and the process wins.** Every emoji on Home means exactly one thing, and a track's emoji and the word beside it are read off the same row, so they cannot disagree. Where the two sources of a track's state contradict, one ladder decides: alive → `🏃 running` · else board=blocked → `⛔` · else done/merged → `✅` · else `⏳ queued`. **The ladder is `cc-reconcile`'s, not the tab's** — it decides, writes the verdict to its snapshot, and Home *renders* that. A dashboard that re-derived state would be a second decider, and the two would disagree in front of the owner. **Process presence wins** — a `claude` running in the worktree is the strongest fact the box has — but the disagreement is never swallowed: the line stays `running` and appends `· board stale`. No line shows two states, and an unrecognised status is `queued`, never a stateless "?".
- **The two lists the owner opens the tab for are whole.** BACKLOG and NEEDS YOU print *every* row (owner, 2026-08-30). They used to stop at 3 and 4 with a "+k more" that sent the owner out of Slack to read the rest — a tab that hides the very thing it exists to show. Neither costs a block to grow: each is one section however long it gets, so the only cap left is `home_list`'s character budget for one Slack text, and that is a safety valve, not a policy — it appends "+k more" only where a row would otherwise be cut in half. The backlog's budget is the tighter one, so a board long enough to strain the view loses backlog lines before ❓ lines.
- **A Home button is not a permission.** App Home is published *per user*, so everyone gets their own copy of the buttons — including "Restart cc-slackd". `home_allowed(user, owner)` gates every `action_id` on the paired owner's Slack user id before anything is read or run; anyone else gets one private line and nothing runs. Restarting a unit is a service change and starting a track is spend, so the one button that would spend hands the owner the command instead of guessing a budget. Every accepted press is logged as well as every refusal: a button that runs silently cannot be debugged. The three board views (To do · Running · Done) sit below the fold and DM one slice each off a single cached board read.
- **Publishing is a snapshot, not a history split.** `git subtree split` republishes every past commit of the prefix, so a name that sat there for one afternoon two months ago ships in `git log -p` forever, and the public repo would need history surgery to take it back. One commit per publish, parented on the public tip, keeps the private history private and makes the gate meaningful: it checks the *only* tree that ever ships. The cost is a per-publish log; merged subjects go in the body and a `Published-From:` trailer makes the next range exact. The boundary itself is a **directory**, decided when code is written, never at publish time — a publisher that could choose paths would be a second, weaker place to get the split wrong.
- **Gates are hooks, not prompts.** CLAUDE.md is advisory; `cc-guard` is enforced. Budget is enforced by `--max-budget-usd` (headless only — interactive sessions have no budget flag; noted in AUDIT).
- **Model default** `claude-fable-5[1m]` at xhigh effort for interactive sessions; loops default to the same but take `--model sonnet` for cheap work.

## 5. Autonomy ladder (how this grows without a rewrite)
L0 you type `cc` · L1 planning session dispatches `--go` workers, you approve PRs · L2 workers self-review, you get pinged only on BLOCKED/decisions · L3 scheduled digests + a planning session you talk to from the phone · L4 "talk to the box" — every rung moves one trigger from you to a script/session; the substrate is the same.
