# Design

Layered: read **1** to get it; go deeper only if you need to.

## 1. Principles (the whole design in five lines)
1. **Claude Code is the runtime.** We never rebuild what it ships (subagents, worktrees, `claude -p`/`--bg`, hooks, cross-session messaging, Remote Control, auto-memory). Our code is thin glue and shrinks as the platform grows.
2. **Deterministic bookkeeping = scripts; thinking = Claude.** Worktrees, commits, pushes, PRs, board, notifications, restarts are scripts that never drift or cost tokens. No always-on "manager agent."
3. **Isolation by construction.** One task = one git worktree + branch (can't overwrite each other). Untrusted/autonomous = Docker container (`ccbox`).
4. **Durable artifacts, ephemeral context.** State lives in files (journal, board, git, PRs), not in a context window. Workers are fresh per iteration; long sessions hand off to a journal and restart clean.
5. **Human gates are permanent and mechanical.** Merge to default branch, spend, external comms, destructive/host ops are blocked by a hook for autonomous and member-facing sessions, and need the owner.

## 2. Architecture (one screen)
| Layer | What | How |
|---|---|---|
| Access | laptop/phone reach the box | Tailscale SSH (primary), a Cloudflare tunnel (backup), a rescue cable on a static address, Claude app via Remote Control |
| Persistence | work survives disconnects/reboots | tmux `main` (user service at boot) hosts every session; `cc` puts sessions in it |
| Sessions | one Claude per unit of work | `cc <repo>` planning session (primary worktree) · `cc <repo> <track>` worker session (own worktree/branch) |
| Autonomy | hands-off execution | `cc … --go "task"` → `cc-loop`: headless `claude -p`, fresh context per iteration, journal-driven, capped by `--max-budget-usd`/turns, ends in a PR |
| Coordination | who is doing what | `cc-board` sidecar JSON per repo (never in git); sessions read/write it; `cc digest` summarizes; daily digest timer |
| Safety net | nothing lost, nothing dangerous | Stop hook `cc-checkpoint` (auto-commit+push in track worktrees only) · PreToolUse hook `cc-guard` (gates, for autonomous *and* member-facing sessions) |
| Human loop | box reaches the owner; owner checks in | `cc-notify` → Slack + ntfy push (+ log); `cc-msg`/`--say` types into a running session; `cc handoff` journals + restarts; `cc-slack` — Slack ↔ sessions on Claude Code *channels*: one Socket-Mode daemon routes `#<repo>` to that repo's live session, replies come back in-thread, sessions autostart |
| Sandbox | unrestricted Claude, contained | `ccbox <name>`: Docker with four mounts and nothing else — `~/dev/<name>` → `/workspace/<name>`, volume `ccbox-claude` (login), volume `ccbox-hist-<name>`, `~/ccbox/allowed-domains` read-only; NET_ADMIN egress allowlist, IPv6 off, memory/pids capped, `--dangerously-skip-permissions` inside only |

## 3. Components (2–3 lines each)
- **cc** — the front door. Repo → planning session; repo+track → worktree session; `--go/--say`; `resume` menu; `done` → PR; `rm`; `handoff`. Repo/track names are validated (no paths, no option lookalikes) and window creation is `flock`ed. Roles are injected with `--append-system-prompt` (no repo-file noise). Deterministic session IDs on the board make resume exact.
- **cc-loop** — the ralph loop. Prompt = task.md + tail of progress.md. Stops on `STATUS: DONE` (→ PR + notify), `STATUS: BLOCKED: q` (→ notify owner), 2 errors, 2 stalled iterations (no commit/journal change), max-iter, or two capped iterations that produced nothing (a cap that still produced work is not a failure). Exit codes are meaningful (0/3/4/5/6/7) and every non-zero one leaves the board `blocked`, never `running`.
- **cc-checkpoint** — Stop hook. No-op unless cwd has a `.cc/track` marker, and it refuses unless HEAD is that track's own branch (a session can repoint HEAD) or when staged names look like secrets (`.env*`, `*.pem/key`, `credentials*`) → reason in `.cc/checkpoint.err`. Push failures are never fatal but never silent either: stderr goes to `.cc/push.err`, which `cc ls`/`cc digest` flag as `push!`. Global gitignore keeps build junk out.
- **cc-guard** — PreToolUse hook. Active for `CC_ROLE=worker|member`, or when the cwd is under a `.cc/track` marker (role=worker) or a `.cc/member-facing` one (role=member) — one walk up, one stat per level, no config to parse; the marker is the truth and can only *tighten* (it beats an inherited `CC_ROLE=worker`), the env var is a convenience. Denies: merge/deploy, push to default/force, external GitHub comms & email, sudo/host/network/service changes, recursive deletes outside the worktree, destructive git/docker, edits outside the worktree (path resolved first, so `../` cannot walk out), ref/HEAD rewrites. Interactive *track* sessions are gated too — the cwd marker is the trigger, by design; only plain operator/planning sessions are untouched. A missing `jq` fails closed for workers and members. **role=member** adds what a session anybody can talk to must not do: dispatch work (`cc … --go`, `cc-loop`, a headless `claude -p`), read the box's secrets (`~/.cc/config`, `~/.ssh`, `~/.claude/settings.json` — through Bash *and* through the file-reading tools), re-wire Slack (`cc slack` off/setup/mkchannel/archive), or write another session's `~/.cc/state`; `cc-notify` stays allowed, because that is how it escalates to the owner.
- **cc-board** — Python, file-locked JSON at `~/.cc/boards/<repo>.json`: tracks, status, notes, PR, session id. `cc board show|add|note|status|json`.
- **cc-notify / cc-msg / cc-digest** — owner push (ntfy topic in `~/.cc/config`), keyboard-injection into a session (tmux), status digest (+ `cc-digest.timer` daily 13:00 UTC).
- **cc-slack** — two roles in one file: `cc-slack daemon` (unit `cc-slackd`) is the box's only Slack connection (Socket Mode delivers each event to a single socket, so one daemon; no inbound port) and a local router on a Unix socket; `cc-slack channel` is the stdio MCP *channel* server every session spawns (user-scope registration; target from the cwd: `~/dev/<repo>` → repo, track worktree → repo/track, `~/dev` → box) — it subscribes to the daemon, pushes `<channel>` events into the session and exposes `reply`/`react`/`file`. A session can **attach a file to its own thread** (`file`: the same three-step upload as the CLI, one `upload_file()` helper) — bounded, because it moves bytes off the box: the path is resolved through symlinks and accepted only under the session's own cwd, `/tmp` or `~/.cc/slack/files`, ≤25 MB, no directories, and with no token (or `chat_id=local`) it lands in the outbox and the tool *says* it was not sent. **Slack channel membership is the access control**: anyone who can post in a routed channel is heard and delivered identically (`role="member"` in the tag), which is why what the box creates is **private by default** and a sub-channel inherits its parent's humans on creation; the owner (pairing) keeps what only the owner may do — DMs, permission answers, `!` commands beyond `!help`/`!status`, `@alias` hand-offs, status marks and App Home. **A reaction is a verdict, and anyone in the channel gives it** (owner's decision, 2026-08-30): a member's `:+1:` on a PR post in `#approvals` squash-merges it, their 🏁 closes a thread, and any other reaction on one of our messages reaches the session with *who* gave it (`user=` + `role=owner|member`), so it can weigh a colleague's 👍 against the owner's — membership of a channel the owner curates *is* the approval gate, and sensitive channels simply have no members. Reactions in a DM stay the owner's (nothing gates a DM and it reaches the box session), and permission answers (`yes <id>`) stay owner-only: authorizing is not the same as judging. The session prompt carries the human half of the same rule — asked by a member for something the box gates on the owner, a session does the ungated part, says which part is not, and @-mentions the owner in that thread (`cc-guard` is unchanged). Permission relay (`yes <id>`), deterministic `!commands` that cost no tokens, autostart of missing sessions through `cc` (never kills a window with a live process). Every outbound post is rewritten once (`linkify_mentions`): an `@handle` becomes a real Slack mention `<@U…>` from a `users.list` table cached 6 h — indexed under the handle, the display and real names and the **first token** of each (`@Alan` for `Alan Turing`, whose display_name is empty), and resolved against the **members of the channel being posted to** (`conversations.members`, cached 5 min) before the workspace-wide table, so one Ada in the channel resolves even when three exist elsewhere. The box's own `@main`/`@<alias>` vocabulary, `@here`/`@channel`, code spans and anything ambiguous or unknown are left as typed (a wrong id pings the wrong human) — and logged, so an escalation that reached nobody leaves a trace. Inbound `<@U…>` renders as that person's *handle* so what a session reads is what it can write back, and a **shared/forwarded message** — whose content Slack puts in `attachments[]`, not in `text` — is folded into the delivered message as one capped bracketed line (`[shared message from #help by ada at …: …]`) instead of arriving empty; Slack's own link unfurls are not folded.
- **cc-publish** — the generic half publishes itself. After a merge lands on the default branch (`cc-slack` fires it off the 👍-merge, plus an hourly catch-up for merges the box never saw), the whole `core/` prefix of `origin/<default branch>` goes to its own public repo as **one commit parented on that repo's tip**. What ships is decided by the directory boundary and by nothing else: it never filters paths, rewrites content or cherry-picks. Its one veto is the **identity gate** — file contents, file names and the commit message it is about to write are checked against this box's user, host and control-repo names (plus `PUBLISH_DENY`), and a hit **aborts loudly** (stderr + `cc-notify` + `~/.cc/state/publish.log`) having pushed nothing. Unconfigured (`PUBLISH_REMOTE` unset in `~/.cc/config`) it is a no-op, so a bare clone never publishes.
- **ccbox** — reference-devcontainer-derived image (node:22); `init-firewall.sh` (the only `sudo` the box user has) resolves `ccbox/allowed-domains` + GitHub's meta ranges into an ipset, allows DNS only to the container's own resolvers, and is re-runnable (resolve → `ipset swap` → rebuild rules); login shared via volume `ccbox-claude`, per-project workspace so it doesn't leak across boxes; tokens via `ccbox/env` (never `~/.ssh`); refuses to sandbox the control repo it lives in.
- **Boot** — `tmux-main.service` (linger) runs `tmux new-session -d -s main -n box … cc-rc` itself, so the server is born in that unit's cgroup and never in a caller's; `cc-rc` waits for internet, runs a Remote-Control Claude named after the box (`$CC_BOX`, default `hostname -s`), respawns (backs off to 120 s + one notification after 5 exits under 15 s). `cc-boot` is `cc`'s idempotent helper: no-op if session `main` exists, otherwise start the unit — it never `restart`s a live server (ExecStop is `tmux kill-server`). `cc-heartbeat` (10 s fsync'd stamp) + `cc-boot-notify` (one message per boot, stamped only once a channel took it) date and announce every power cut.

## 4. Decisions and what we deliberately did not build
- **No fleet, no always-on overseer.** Research (Anthropic's multi-agent writeup; Cognition's "Don't build multi-agents"; METR half-life data) says coding rewards one strong linear agent with fresh context per chunk, not many parallel agents. Parallelism = 2–4 independent worktrees, not 20. An always-on coordinator burns tokens and rots its own context; everything it would do mechanically is a script.
- **No custom message bus.** Claude Code has native cross-session messaging (`SendMessage`, push-based, zero idle cost) and Remote Control. We only added what doesn't exist natively: **owner notification** (Slack/ntfy), a **deterministic waker** (`cc-msg`), and — until 2026-08-27 — a **read-only MCP** so Claude.ai could check in (auth delegated to Cloudflare's MCP portal, secret upstream path, one-command off switch). Retired once Slack covered the same need with one fewer public surface — the code stays parked in the private overlay.
- **Slack via native channels, not a bot framework or Claude Tag.** Claude Tag runs cloud sessions and can't reach this box; a Bolt bot with `claude -p` per message would rebuild sessions. Channels deliver into the session that already exists (same one you see in tmux and Remote Control). Cost: it is a research preview, so sessions carry `--dangerously-load-development-channels server:cc-slack` and the flag may change; the daemon is ~600 lines of stdlib Python (slack_sdk only for the WebSocket).
- **`cc-board` vs native agent-teams.** Agent teams (experimental) overlap the board. We keep the board (simple, stable) and will drop it when the native feature is GA.
- **`--go` (headless, capped) only.** `--bg` (native background sessions) is not wired into `cc`: `--go` is deterministic, budget-capped and journal-driven, and one worker mode is easier to reason about than two.
- **Context strategy = both.** Ephemeral workers (loop) and restart-rehydrate (`cc handoff`) share the same journal, so nothing is decided up front.
- **A member-facing session is marked, not instructed.** Put `.cc/member-facing` in a folder (`~/dev/help/.cc/member-facing`) and every session started there is role=member: `cc` exports `CC_ROLE=member` and adds one sentence to the prompt, but the gate is the marker — `cc-guard` finds it by walking up from the cwd, so it holds for subagents, for a session started by hand, and with no env at all. Only the owner lifts one, per call. **The honest ceiling:** the command gates are a *blocklist*, not a sandbox — they stop accidents and casual prompt-injection, not a determined attacker (a redirection, a copied binary, a script written first). Real containment is `ccbox`; run a member-facing session there when the threat model needs more than a gate.
- **A channel is a session; no channel is a dead end.** Every channel the bot is in answers. One that maps to no project *becomes* one on its **first message** — never in advance, never on channel creation: `~/dev/<channel name>` (lower-cased, folded to `[a-z0-9-]`) with a `CLAUDE.md` rendered from `templates/channel-CLAUDE.md`, the marker `.cc/member-facing`, and `git init`, then the ordinary autostart delivers the message. **Member-facing by default is the point:** a channel anybody can create must not yield an ungated session, so `cc-guard` gates it from its first tool call and it is read-only outside its own directory; anything that needs a change goes to the owner (mention + `cc-notify`). Bounded at 3 new dirs an hour (`~/.cc/slack/provisioned.json`) so a channel-creation spree cannot spawn sessions without limit — an already-provisioned dir is then reused forever, the cap is on creation only. Never for DMs (owner-only, and they reach the box session), `#approvals`/`#alerts`, a sub-orch channel live or archived, or a name that normalises to nothing: those keep the old "no project maps" behaviour. A `#<repo>--<track>` channel whose window is a headless `--go` worker is never restarted and never left silent either — the question goes to the `<repo>` session prefixed `[asked in #<repo>--<track> while its headless worker runs]` and one line in the channel says so. Promoting one to a real project stays the owner's move: move or rename the dir, add a git remote, drop the marker.
- **The App Home tab is a hierarchy, not a dump.** `home_blocks(st)` is a pure state→blocks function (`home_parts` builds it, `home_cut` trims it), so the whole layout is asserted on fixtures — busy / quiet / degraded / overflow — rather than eyeballed, and the busy one is pinned by *equality* against the design handoff's own reference JSON. The order is fixed and answers the owner's two questions in that order: **header** (the box, and when) → **RUNNING n · BLOCKED n · QUEUED n** with one dense line per thing actually running (a unit that is down and a Claude usage limit sort above them: the owner must not scroll to learn the box is impaired; nothing running is a *sentence* with the last thing that finished, never a gap) → **NEEDS YOU · n**, the one band that answers "does this need me?" → up to three **buttons** → a **divider**, the fold, below which everything is secondary by contract: the backlog (≤3 + a count), the channels where something is actually happening (the quiet ones are a number, never lines), then load, audit and units+boot as grey `context`. Phone first: one line per item, ~40 rendered characters, no two-column `fields` anywhere (they truncate at ~40 chars, and a phone is the only screen this is read on). Nothing ever renders a label with nothing under it. Budget ≤16 blocks; when even that will not fit, `home_cut` drops in the owner's order — boot, audit, channels, backlog — and what is *running* or *needs them* is never what gets cut.
- **A needs-you row carries the ask, not a count.** `❓ *#repo* · 12m · pick a branch name` — where, how long it has waited, and the thing the owner can answer without opening anything; `❓ 2 threads waiting` is the line that made them open Slack to learn what the box already knew. The age and the ask come out of the snapshot `reconcile_reactions` already holds, so the dashboard still makes **no Slack read of its own** and there is still exactly one writer per mark. The band merges threads (oldest first), PRs owed a 👍 and blocked tracks into one notation, caps at four lines, and is *absent* — never present-and-empty — when nothing needs them.
- **One vocabulary, and the process wins.** Every emoji on Home means exactly one thing (`HOME_STATE` plus 🔴 a unit down, 🟢/🟡/⚪ a channel's session, ❓ waiting on the owner, 🔧 work with no track), and a track's emoji *and* the word beside it are read off the same row — they cannot disagree. Where the two sources of a track's state contradict each other, one **ladder** decides: alive → `🏃 running` · else board=blocked → `⛔` · else done/merged → `✅` · else `⏳ queued`. **Process presence wins** — a `claude` running in the worktree is the strongest fact the box has, and it is the fact the owner is asking about — but the disagreement is never swallowed: the line stays `running` and appends `· board stale`, so the owner can see *which* source is behind. No line ever shows two states, and an unrecognised status is `queued`, never a stateless "?".
- **A Home button is not a permission.** The App Home tab is published *per user*, so every person the box publishes to gets their own copy of the buttons — including "Restart cc-slackd". `home_allowed(user, owner)` gates every `action_id` on the paired owner's Slack user id before anything is read or run; anyone else gets one line back privately and nothing runs. Restarting a unit is a service change and starting a track is spend, and both are the owner's to authorise — so the one button that would spend (`Start next track`) hands them the command instead of guessing a budget for them.
- **Publishing is a snapshot, not a history split.** `git subtree split` republishes every past commit of the prefix, so a name that sat there for one afternoon two months ago ships in `git log -p` forever — the public repo would need history surgery to take it back. One commit per publish, parented on the public tip, keeps the private repo's history private and makes the gate meaningful: it checks the *only* tree that ever ships. The cost is that the public repo's log is per-publish, not per-commit; the subjects of the merged commits go in the body, and a `Published-From:` trailer makes the next range exact. And the boundary itself is a **directory**, decided once when code is written, never at publish time — a publisher that could choose paths would be a second, weaker place to get the public/private split wrong.
- **Gates are hooks, not prompts.** CLAUDE.md is advisory; `cc-guard` is enforced. Budget is enforced by `--max-budget-usd` (headless only — interactive sessions have no budget flag; noted in AUDIT).
- **Model default** `claude-fable-5[1m]` at xhigh effort for interactive sessions; loops default to the same but take `--model sonnet` for cheap work.

## 5. Autonomy ladder (how this grows without a rewrite)
L0 you type `cc` · L1 planning session dispatches `--go` workers, you approve PRs · L2 workers self-review, you get pinged only on BLOCKED/decisions · L3 scheduled digests + a planning session you talk to from the phone · L4 "talk to the box" — every rung moves one trigger from you to a script/session; the substrate is the same.
