# <box> — Usage

Shallow first. Each section: the 2–3 things you actually type. Why it is shaped this way: `docs/DESIGN.md`. Talking to projects and agents, and the Slack mechanics: `COMMS.md`.

## Connect
- Laptop: `ssh <user>@<tailscale-ip>` (Tailscale) · anywhere: `ssh <box>` (Cloudflare, OTP) · rescue cable: `ssh <user>@<rescue-ip>`
- Phone: Claude app → Code → session `<box>` (Remote Control). Shell on phone: SSH app over Tailscale → `tmux attach -t main`.
- Work survives disconnects because it runs in tmux `main`. Detach: `Ctrl-b d`. Reattach: `tmux attach -t main`.

## Sessions (`cc`)
- `cc <repo>` — planning session for `~/dev/<repo>` (main branch; plans, dispatches, reviews PRs). Merging is yours unless you grant it standing — then it reviews and runs the gates first, and says what landed; the grant waives no other gate.
- `cc <repo> <track>` — worker session on its own worktree + branch `track/<track>`. Auto-commits and pushes after every turn. Finish with `cc done <repo> <track>` → PR.
- `cc <repo> --orch <alias> ["brief"]` — a peer orchestrator in the primary worktree, addressable as `@<alias>` in that repo's channel and in its own `#<parent>-<alias>-<id>` (routing table `~/.cc/slack/orchs.json`). Archived when the session exits, by `cc slack archive <#chan>`, or by the daily janitor 24 h after it is gone.
- `cc` on its own attaches the tmux session. `cc resume` — menu of all sessions by name/status. `cc ls` / `cc digest` — what's running and where things stand, each track with how full its context is.
- `cc-context [<repo> <track>]` — how full a session's context REALLY is, read off its own transcript (used/window, and where the window figure came from). The Stop hook records it after every turn and, once per line crossed, tells a track session what to do: **30% — write the handoff entry now**, **40% — hand off**, **60% — hand off regardless**. On the 1M window the box runs that is 300k / 400k / 600k; each line has a floor (never under 60k / 90k) so the rule still works, and still leaves room to work, on a 200k model. Early on purpose — a session well inside its window answers better than one near the top of it. The 40% handoff is *pending*, not immediate: it waits for a turn with nothing in flight (no background task, no unfinished merge, nothing uncommitted or unpushed); only 60% goes anyway. Every crossing is appended to `~/.cc/state/context/handoffs.jsonl` — `cc-context --handoffs` reads it, `wc -l` counts it. Tune in `~/.cc/config`: `CC_CONTEXT_WARN_PCT` / `CC_CONTEXT_HANDOFF_PCT` / `CC_CONTEXT_CEILING_PCT` and the two `_MIN` floors.
- `cc-owed [<repo> <track>]` — what a session still owes Slack: a message nothing answered, or its own question posted without `needs_owner` (on nobody's NEEDS YOU list). The same Stop hook says it once, with the `reply(...)` call that pays it — the box tells the session instead of the session remembering. `cc-owed --ledger` counts every debt ever said.
- Reconnect = the same `cc …` command. `cc -c <repo> [track]` only if the process died. `cc rm <repo> <track>` removes a track (worktree, local branch, board entry, state).
- **`cc-pulse.timer` wakes the box every 2 h** — every repo with a board and every live orch, enumerated at run time, and a quiet board is still woken: driving the sessions is the point. What it does first is read the files, so the tick CARRIES them — the `main-gate` row, open `cc-scope` asks, the rows queued or blocked and the rows still in flight (a PR in `review` above all) — and a session with nothing to do costs one cheap turn. Two targets it spends nothing on: a repo whose board rows are **all `kind=session`** (a channel/course repo, driven by its channel) is never pulsed, and a session woken with nothing due leaves a mark, so the next pulse inside `CC_PULSE_QUIET` (6 h, `~/.cc/config`) skips it unless something is due by then. A target with no session gets an idle one; a live one is typed one line and decides for itself what to do (`WORKING.md` order, then `~/.cc/state/<target>/goals.md`). It never wakes a session that is mid-handoff, mid-turn, showing a dialog, or woken in the last 90 min. **The timer is installed switched off** — read one `cc-pulse --dry-run` and enable it by hand; after that `CC_PULSE=0` in `~/.cc/config` stops the whole loop and `touch ~/.cc/state/<target>/pulse.off` excuses one target. Preview with `cc-pulse --dry-run` — who would be woken, who is skipped, and why — one target with `cc-pulse <repo>`; the same lines are in `~/.cc/state/pulse.log`.
- **`cc-janitor.timer` sweeps up every Sunday**, in the repos you list as `CC_JANITOR_REPOS` in `~/.cc/config` and no others: tracks merged or done for over 48 h (`cc rm`), `track/*` branches on origin whose PR is merged, and empty tmux windows. Uncommitted work, a PR that closed without merging, a branch nobody opened one for and anything still running are **reported, never removed**. A `ccbox-*` container stopped for 7 days (`CC_JANITOR_CONTAINER_DAYS`; 0 turns it off) is removed too, on every box and whatever `CC_JANITOR_REPOS` says — the image stays, but **a stopped ccbox is gone after a week**, so anything a run must keep has to be out of the container by then (ccbox runs already write theirs into the mounted project dir). Preview a pass with `cc-janitor <repo> --dry`; what it did is in `~/.cc/state/janitor.log`.
- `cc rc status|restart` — the always-on box session in window `box`; restarting ends its current conversation, so pick `<box>` again in the app.
- Slack, the phone app and tmux can hold the *same* session at once. Between sessions Claude uses its native `SendMessage` (session name = window name); you don't relay.

## Autonomous work (hands-off)
- `cc <repo> <track> --go "instruction"` — headless worker: fresh context per iteration, journal at `~/.cc/state/<repo>/<track>/progress.md`, ends with a PR and a phone push. Options: `--loop N` (iterations, default 1) `--budget USD` (per iteration, default 8) `--turns N` (default 80) `--model sonnet`.
- It stops and pings you if BLOCKED, stalled, or capped twice with nothing to show. To answer a BLOCKED: append to `~/.cc/state/<repo>/<track>/task.md`, delete the `STATUS:` line from `progress.md`, then `cc <repo> <track> --go ""` (empty instruction = re-dispatch the task already there). Nothing merges to main without you.
- `cc <repo> <track> --say "text"` — talk to a running *interactive* session; a headless worker's pane is a shell, so it refuses and points you at task.md. `cc handoff <repo> <track> [--over PCT]` — journal + fresh context; `--over` (bare, or with a percentage) hands off only if the measured context really is that full, and refuses rather than guess when it cannot be measured.
- **One command lands it: `cc-land <repo> <pr-number> [<pr-number> …]`.** Gates, merge, the `#approvals` card marked 👌, board, ask ledger, `install.sh`, switching on any unit the change *added*, and restarting only what moved — in that order, one line each. **Your 👍 on the card runs the same sequence**, off the reaction thread, so a merge you approve from your phone deploys itself; nothing depends on a session remembering to type this. Several PRs merge one by one and deploy once, at the end. A failure that would leave the box wrong (gate, merge, install, unit, restart) stops everything; a failure in the bookkeeping (card, board, ledger) is reported and the rest still runs — exit 3 means "deployed, one of those wants a hand". Work with no PR (a config edit, a host change) closes the same way: `cc-land <repo> --track <t> --note "<what changed>"`. It never merges on a promise (gates run on the PR's own head, in a throwaway worktree), never gates a PR that is already in, never switches on a unit that is off for a reason, and never restarts the box's tmux server. Re-running is the recovery and is safe. Workers cannot call it — `cc-guard` denies it exactly as it denies `gh pr merge` and `systemctl`.

## Sandbox (`ccbox`) — untrusted or fully unrestricted work
- `ccbox <name>` — Claude with `--dangerously-skip-permissions` in Docker; only `~/dev/<name>` is mounted, at `/workspace/<name>`, and `~/.claude` is the box's own volume (`ccbox-claude-<name>`; a new box gets just the login copied in from the newest existing one), so sessions, memory, history and trust never bleed between projects — the login is the one thing boxes share. Egress is limited to `~/ccbox/allowed-domains` (`--open-egress` lifts it); `-c` = `claude --continue`. Tokens: `~/ccbox/env` — missing → it refuses (`cp env.example env`, chmod 600). `ccbox <control-repo>` is refused: that repo's `core/bin/` is the host's `~/bin`.
- `ccbox ls | stop | rm | shell <name> | logs <name> | build [<name>]`. `ls` shows each box's egress mode; `logs <name>` shows the firewall run — a `WARN: could not resolve …` line means that domain was skipped and is *not* reachable. Inner tmux prefix is `C-a`.
- Options apply when the container is **created**: on a running box `ccbox <name> --open-egress|-c` refuses rather than silently attach — `ccbox stop <name>`, then start it again. A stopped box is recreated from the image, so installed packages and `/tmp` are lost; `/workspace/<name>`, its `~/.claude` volume and `/commandhistory` survive. `ccbox build` after editing `~/ccbox/*`.
- Project images: `ccbox build <name>` builds `ccbox-<name>:latest` from `~/dev/<name>/docker/Dockerfile` and `ccbox <name>` picks it up (`--image IMG` overrides). Headless: `ccbox <name> --cmd "..."` runs that command instead of interactive claude; from a terminal it runs in tmux and a shell follows it, without a TTY (a timer, a worker) it runs without tmux — ccbox prints its output and exits with its status, both kept in `ccbox logs <name>`. Images may ship `/usr/local/bin/ccbox-project-init` (runs at start).

## Usage limits and model fallback
- **Claude usage limits are waited out, not failed.** A rate-limited run is neither an iteration nor an error: `cc-limit` stamps `~/.cc/state/claude-limit` with the reset time, every loop and the box session wait for it, you get **one** push per episode (`<box> limit` → `#alerts`), and the same iteration reruns. A limit outlasting 6 h (`CC_LIMIT_MAX_WAIT`) exits the loop with **8** and pings you. `cc-limit status` by hand; `cc ls` / `cc digest` print `⏳ Claude usage limit until 11:40Z` while it is on.
- **A usage limit on the primary model moves every session to the fallback, and back.** `cc-model.timer` ticks every 60 s and switches when `cc-limit`'s stamp names the primary (`CC_MODEL_PRIMARY`), or a live pane shows a fresh `usage limit` line *and* a one-turn probe agrees. Live interactive sessions are retyped to `/model <fallback>` (`CC_MODEL_FALLBACK`); headless workers pick it up from `cc-model current` next iteration. One line per switch (`<box> model` → `#alerts`). It probes the primary after the reset time (at most every 15 min) and restores on the first answer. `cc-model status` → the current model or `<fallback> until 11:40Z`; override in `~/.cc/state/model-override`, log in `~/.cc/state/model.log`; never two switches within 10 min, and effort stays what `~/.claude/settings.json` says.

## Your asks (`cc-scope`)
- The board is what the box **took on**; the ledger is what **you asked for**. One row per ask, opened when you make it, closed only against evidence (`~/.cc/scope/<repo>.json`).
- Captured automatically: a `UserPromptSubmit` hook reads every prompt a non-worker session gets — typed in the terminal or arriving from Slack — keeps the directives and files them under that session's repo. Acks, plain questions and `!`/`/` commands are skipped, but every message it saw is logged: `cc-scope missed [<repo>]` shows what it did not open, `cc-scope add <repo> "…"` fixes a miss. The same ask twice bumps a counter instead of opening a second row — `⚠ asked 2×`.
- An ask moves **open → claimed → merged → delivered → verified**, or leaves the queue as **declined**. `cc-scope list [<repo>]` is everything not yet settled; `show <repo> <id>` is one in full, with the separate directives a compound ask contains; `claim`/`track`/`note` as it moves.
- **Merged is not delivered.** A merge puts code on a branch; it does not put anything on your screen — the daemon runs the old code until it restarts, the file is not linked until `install.sh` runs. So a PR number no longer closes a row, and no sentence does. A row names its **own check**: a command whose exit code decides. `cc-scope check-cmd <repo> <id> "<cmd>"` gives it one, `deliver <repo> <id>` **runs** it, and only exit 0 delivers. `cc-land` does this for you, last, after the restart.
- **A row with no check is `unverified`, not done** — it stays on the queue and says so (`cc-scope unverified [<repo>]`). Not every ask can be measured by a command; where none can exist, `verify <repo> <id> --evidence "what you looked at"` is you putting your own name on it, and it is refused while a check the row names is red. An honest "nobody checked" is the point.
- **A session may decide NOT to do something you asked** — `decline <repo> <id> --why "…"`. The reason is required and is kept beside the ask: a declined item stops counting as work but never leaves the ledger. An omission leaves an open item, a decision leaves a reason, and nothing silently vanishes between the two.
- **'Done' is measured against it**: `cc done` prints that track's unsettled asks before it opens the PR, `cc-scope check <repo> [--track T]` exits **1** while any remain, and `cc digest` carries one line — *N asks of yours still open*. Bulk load or replay: `cc-scope import <repo> <file>` (6 tab-separated columns, idempotent; your overlay's seed file).

## The board vs the box (`cc-reconcile`)
- `cc-reconcile.timer` runs `cc-reconcile --apply --notify` every 20 min and 5 min after boot. It **fixes what has one right answer** — a track still `running` with no worker anywhere, a `review` whose PR merged, a `merged` whose PR is still open — writing through `cc-board`, so every change lands as a `reconciled: … → …` note on that track. Nothing else is touched: it never deletes, merges or opens anything.
- **What it cannot decide, you hear about** (once a day per finding, `#<repo>` or `#alerts`): a PR closed without merging, a worktree that is gone, a checkpoint that would not commit, a `review` with no PR, a worktree with no board entry. A track that stopped with nothing in its journal is set to `blocked` *and* reported — that one is both. So is a **runaway it ended** (below).
- Alive means: a `claude` in the track's worktree, a `cc-loop <repo> <track>` (alive for hours with no claude while it waits out a usage limit), or a live pane in its tmux window. Any of the three and the board is corrected *towards* running, never away from it; anything the board touched in the last 10 min is left alone (`--grace`).
- **`waiting` is not `running`, and alive is not the test.** A track whose journal's newest line is `STATUS: BLOCKED: <question>` is set to **`waiting`** — a person must answer before anything happens — even with a live process in its worktree, and it is reported for as long as the question stands. That word is the only thing that reaches your NEEDS YOU list. A loop sitting out a usage limit is **held on the clock**: its own row, never yours to act on. A worker between iterations declared nothing and is simply `running`. Nothing is ever read out of journal prose — the session declares, or it does not count.
- By hand: `cc-reconcile [repo …]` reports and changes nothing, `--apply` fixes, `--json` for machines, `snapshot` prints the effective state of every track (`view`: the same as TSV, what `cc ls` and `cc digest` read), `selfcheck` for the decision table. Exit **1** = something needs you. Log: `~/.cc/state/reconcile.log`.
- **One decider** (review rec #7): every unfiltered run writes `~/.cc/state/reconcile.json` — effective state, live presence, who each track waits on and why. `cc digest` and `cc ls` read it instead of guessing, and fall back to the board when it is missing or over an hour old.

## A loop that is working carries on — one that is not gets stopped
- **There is no spend cap anywhere** (some jobs are legitimately expensive). What ends a loop is not being dear, it is not producing.
- **The step limit is a checkpoint, not a verdict.** `cc-loop` reaching `--max-iter` with work *committed* in that iteration buys itself another N and carries on, as often as it keeps committing — a board note each time. An iteration that committed nothing stops at the limit as before (exit **6**), and neither a `STATUS: BLOCKED` nor a run of errors is ever carried on.
- **Runaway, from inside the loop** (exit **9**): three iterations *in a row* that show nothing for their money, each judged against this track's own history — committed nothing and left the journal untouched · repeated the previous outcome verbatim with no commit · spent 5× what a committed iteration costs *this* track with no commit for two iterations. One of those is an ordinary hour; three consecutively is a loop going nowhere. It stops itself, the board says `blocked`, and you get one line with the numbers.
- **Runaway, from outside** — the one `cc-loop` cannot catch is its own: `cc-reconcile` ends an **orphan** (a headless worker with no `cc-loop` above it — nothing will time it out or commit what it writes) on sight, and a **wedged** loop (alive, nothing moved for 3 h, no usage limit to be waiting on) after two runs 20 min apart have both seen it. `--no-stop` reports without ending anything.

## Recurring audit (`cc-audit`) — hands-off, never fixes anything
- `cc-audit.timer` runs `cc-audit auto` daily at 03:30 UTC and picks the mode from the date: **day 1 → monthly**, else **day 8 → arch** (the codex architecture review), else **day 15 → delete**, else **Sunday → weekly**, else **every 3rd day-of-year → review**, else it runs the suites and nothing else — quiet to you, not blind to a red `main`. By hand: `cc-audit checks|review|weekly|monthly|delete|arch|selfcheck [--dry] [--no-post]` (`--dry` touches nothing, `--no-post` writes the file but skips Slack).
- **checks** (no LLM, ~3 min): the suites (`tests/check.sh`, `tests/selftest.sh`, `cc-slack selfcheck`, `tests/slack_sim.py`), user units, heartbeat freshness, Slack daemon and its errors since the last report, disk/load, settings drift vs `config/claude-settings.json`, `~/bin` and home-doc symlinks, leftovers and worker spend — one PASS/FAIL line each. Every other mode runs it first.
- **The `main-gate` row owns a red baseline.** Whatever the mode, the first failing suite becomes ONE board track `main-gate` (queued) naming the gate and the first line of the failure; an unchanged red leaves it alone, a different failure updates it in place, green closes it, and once somebody starts it, it is an ordinary track. So a session sees main is red *before* it dispatches, instead of every track rediscovering it and disclaiming it.
- **review** (every 3rd day — the one you actually read): checks, plus a read-only LLM pass over **how well the box served you**. Sections: responsiveness, communication quality against your own style rule (it quotes the worst offender), work outcomes, breakages, **what you had to do by hand that should have been automatic**, and the 3 most valuable improvements.
- **weekly** = checks + a read-only code audit of one area, rotating by ISO week: cc core → cc-slack → ccbox → boot/notify/install/docs. **monthly** = all four plus a synthesis, and it puts the findings on the board as track `audit-<yyyymm>` (todo) — to be dispatched **when you say so**.
- **delete** (day 15 — a *second opinion, from another model*): checks + one read-only `codex` pass over the same evidence, asked one question — **what should simply go**. Findings land on the board as `delete-<yyyymm>`, like monthly's. It is a backend swap inside `cc-audit`, not a second audit system.
- **The codex wall is codex's own, and weaker than the Claude one**: `--sandbox read-only` plus `--ignore-user-config`/`--ignore-rules`, so the model *may* run read-only shell commands — where the Claude passes have no shell at all. It still cannot write. **Needs `codex login` on the box**: until then every `delete` run writes a one-line _postponed_ report, says so in Slack and exits 0 — same for a box with no codex at all. `cc-audit selfcheck` proves those paths with no network and no spend.
- Model and effort come from `~/.cc/config` (`CODEX_MODEL`, `CODEX_EFFORT`; the environment wins). Both optional: unset means the flag is not passed and codex uses its own default. Effort rides as `-c model_reasoning_effort=<v>` — there is no `--effort`. `cc-audit` reads only those two keys and never sources the config, so no token reaches the model.
- **The Claude passes cannot change anything, by construction.** `cc-audit` gathers the evidence itself into `~/.cc/state/audit/<date>-<mode>/evidence/` (scrubbed of any `xox…` token), then runs the model with no shell and no MCP: `--setting-sources ''`, `--strict-mcp-config`, only `Read,Grep,Glob,LS`, everything that writes, runs or posts denied by name — including `Monitor`, which reaches a shell and once got through a `Bash`-only deny. `~/.cc/config`, `~/.ssh`, `~/.claude.json` and the credentials file are denied to `Read`/`Grep` too.
- Reports: `~/.cc/state/audit/<date>-<mode>[-<area>].md`, evidence beside them, log `~/.cc/state/audit/audit.log`. Slack gets **one line**; the full report replaces the `#<box>` canvas. A failed or budget-cut run says `<mode> failed (see audit.log)` rather than reporting zero findings.

## Does the box still work? (`cc-evals`)
- `cc-evals run` — the **regression set**: frozen replays of work this box has already landed, each proved on a pinned base snapshot (the probe must FAIL there) as well as on this tree, plus the control-plane properties. Seconds, no spend, red or green — and the nightly audit runs the same set as one more `## suites` gate, so a red eval is the same single `main-gate` row as any other red baseline.
- **What it covers today is the control plane and the worker guard**: every case drives this box's own scripts, none calls a model, so it does not yet gate a model, prompt or harness change — that needs a model-backed capability case, and there is none. `--set all` adds the graded capability case; `list | last | bless <case>` (blessing is the owner's, at a terminal). One file per case in `evals/cases/`, answers are salted digests in `~/.cc/evals/refs`, outside every git tree.

## What must be installed (`cc-units`, `cc-settings`)
- `cc-units check` — every core user unit against `config/units.json`, the one list: enabled, active, and for a timer *armed* (active with no next trigger is down). `cc-units list|restart-for <files>` shows the manifest and what a change would need restarted. Adding a timer = its two unit files + one row.
- `cc-settings check` — names exactly which managed Claude hook or deny rule is missing from `~/.claude/settings.json`; your own keys, theme and extra rules are never drift. Both run inside `cc-audit checks`.
- **`cc-settings apply` is yours alone** — at a terminal, not in a session, not in a track worktree. It backs up, adds only missing *hooks*, never touches `permissions`, and prints missing deny rules for you to paste.

## Notifications
- Sessions and loops call `cc-notify "…"` when they finish or need you → **Slack** (webhook in `~/.cc/config`) and **ntfy** push (subscribe the phone to the topic from `cc-notify setup`). Daily digest at 13:00 UTC. Log: `~/.cc/notify.log`.
- That key, and every other one, lives in `~/.cc/config`, and `cc-config get|set|unset|list` is the only way in or out of it: the environment wins over the file, writes are locked, and nothing anywhere *sources* it — a value is a string, never code.
- Every boot posts one message (`cc-boot-notify`): time up, whether the last boot ended cleanly or by power loss, and seconds dark. `cc-heartbeat` keeps a 10 s fsync'd stamp; events accumulate in `~/.cc/state/power-events.log` (`cause=clean-reboot` or `cause=power-loss`).

## Slack, two-way (`cc slack`)
How the conversation itself works — channels, threads, marks, who may do what, the free `!` commands and the agent-facing `cc-slack` ones — is `COMMS.md`. Here: the setup and the box-side commands.
- One Slack app ("<box>", Socket Mode: no inbound port, no tunnel). Once: `cc slack setup` prints the 5 steps — create the app from `slack/app-manifest.json`, `cc slack setup --bot xoxb-… --app xapp-… --owner-email you@x`, `cc slack on`, then `cc slack mkchannel <repo>` per project (**private by default**, `--public` opts out; a `#<repo>--<sub>` name inherits `#<repo>`'s people). The bot cannot create the app itself.
- `cc slack status|channels|off|archive <#chan>`. Extra routes: `~/.cc/slack/routes.json`. From the shell, `cc-slack inject <target> "text"` pushes a message the same way; with Slack off the reply lands in `~/.cc/slack/outbox.log`. `cc-notify` posts into `#<repo>` when the title starts with a repo name.
- Sessions pick up their channel when (re)started after `cc slack on` — for the boot session see RUNBOOK. Built on Claude Code *channels* (research preview, loaded with the development flag).
- **Merge PRs with a 👍.** `cc done` posts `[<repo>] PR #<n>: <title> — <url>` into `#approvals`; react 👍 on that message and the box queues a landing job — the gates run against the PR's own head, and only on green does it merge, install and restart what moved — answering in the thread. One card per PR: whoever gets there second finds the first and posts nothing. Manual post: `cc-slack post-approval [--force] <repo> <n|url>` (`--force` re-posts after a failed merge). A merged PR never gets a card: the landing edits its card to `landed ✓`, and `cc-slack approvals-sweep` (given a turn by cc-reconcile) does the same to any card the landing missed. Needs `reactions:read` + the `reaction_added` event in the manifest (reinstall after changing it).
- **Live dashboard — tap the bot in the Slack sidebar → *Home*.** Units 🟢/🔴 + disk/load + any usage-limit stamp; one line per channel with its session and open ❓ count; every board track with iteration, cost, PR state and `commit!`/`push!` flags; the newest `cc-audit review` verdict and the last boot. Needs `home_tab_enabled` + the `app_home_opened` bot event — **re-paste `slack/app-manifest.json` (or `cc-slack manifest …`), hit Reinstall, then `systemctl --user restart cc-slackd`**; without them the daemon logs one line and leaves the tab alone.
- `cc quick doing|done "…"` — log work that has no track; Home lists what is in progress.
- **24 h of vitals (`cc-vitals`).** `cc-vitals show` draws the last day of CPU, RAM, load, temperature, power and disk as one chart — every series a percentage of its own capacity on a single 0-100 axis, the legend carrying the real numbers. `cc-vitals record` is the recorder behind it (one row a minute: counters by delta, gauges by mean-and-max) and it is installed OFF (`enable: owner` in units.json — `systemctl --user enable --now cc-vitals.timer` switches it on) — a day of history sits in `~/.cc/state/vitals/`. `cc-vitals render` redraws `current.png` (matplotlib, headless Agg) and `current.txt` (block-glyph, always available as the fallback); `--if-stale` keeps it from redrawing a 24 h chart every minute.
