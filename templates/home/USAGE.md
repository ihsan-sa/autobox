# <box> — Usage

Shallow first. Each section: the 2–3 things you actually type. Why it is shaped this way: `docs/DESIGN.md`. Talking to projects and agents, and the Slack mechanics: `COMMS.md`.

## Connect
- Laptop: `ssh <user>@<tailscale-ip>` (Tailscale) · anywhere: `ssh <box>` (Cloudflare, OTP) · rescue cable: `ssh <user>@<rescue-ip>`
- Phone: Claude app → Code → session `<box>` (Remote Control). Shell on phone: SSH app over Tailscale → `tmux attach -t main`.
- Work survives disconnects because it runs in tmux `main`. Detach: `Ctrl-b d`. Reattach: `tmux attach -t main`.

## Sessions (`cc`)
- `cc <repo>` — planning session for `~/dev/<repo>` (main branch; plans, dispatches, reviews PRs). Merging is yours unless you grant it standing — then it reviews and runs the gates first, and says what landed; the grant waives no other gate.
- `cc <repo> <track>` — worker session on its own worktree + branch `track/<track>`. Auto-commits and pushes after every turn. Finish with `cc done <repo> <track>` → PR.
- `cc <repo> --orch <alias> ["brief"]` — a peer orchestrator in the primary worktree, named `<alias>@<repo>` wherever the box shows it to you (`cc ls`, `cc slack status`, the dashboard) and addressable as `@<alias>` in that repo's channel and in its own `#<parent>-<alias>-<id>` (routing table `~/.cc/slack/orchs.json`). Archived when the session exits, by `cc slack archive <#chan>`, or by `cc-reconcile`'s daily sweep 24 h after it is gone.
- `cc` on its own attaches the tmux session. `cc resume` — menu of all sessions by name/status. `cc ls` / `cc digest` — what's running and where things stand, each track with how full its context is.
- `cc-context [<repo> <track>]` — how full a session's context is: the harness's own number, off `cc-statusline`'s per-session file (`~/.cc/state/statusline/<session-id>.json`, wired as `statusLine`) when it is fresh, else read off the transcript (used/window, and where the window figure came from) — the answer always says which. One hand-off line, absolute: `CC_CONTEXT_HANDOFF_TOKENS` in `~/.cc/config`, default 150k. Past it the line says *hand off* and a bare `--over` exits 0; the session then runs `cc-handoff --overlap <target>` itself — a spend choice; past the rotate line above it (`CC_CONTEXT_ROTATE_TOKENS`, default 200k) the box opens that overlap for it on the next cc-reconcile tick. `cc-context --all` lists every session with a status-line file under a day old (`cc ls` shows the same per track).
- Reconnect = the same `cc …` command. `cc -c <repo> [track]` only if the process died. `cc rm <repo> <track>` removes a track (worktree, local branch, board entry, state).
- `cc rename <old> <new>` — renames a project everywhere the box keys by its name: `~/dev`, worktrees, state, board, ask ledger, its Slack channels (renamed in place, so their history stays), routes, tmux windows, config keys and records. `-n` prints the whole list and changes nothing; `--stop` stops its live sessions and workers first and starts them again after. GitHub, and prose a person wrote, are left alone.
- **`cc-reconcile`'s tick is the wake now, not a separate timer**: a queued row that can start, or a row that stopped (`blocked` — what a landing that died leaves behind), wakes that repo's planning seat once per state — there is no 2-hourly wake of every session any more. An orch is never woken this way: its own channel and its own workers wake it. **The wake is off until you switch it on** with `CC_WAKE=on` in `~/.cc/config`; unset, each repo's skip is in `~/.cc/state/pulse.log`.
- **`cc-reconcile sweep`** does the daily cleanup once a day inside the tick — `cc-reconcile sweep [<repo>…|--configured] [--dry]`, in the repos you list as `CC_JANITOR_REPOS` in `~/.cc/config` and no others: tracks merged or done for over 48 h (`cc rm`), `track/*` branches on origin whose PR is merged, empty tmux windows, and a worktree the harness left inside a checkout for a subagent that nothing has written to in hours (freeing the branch name it was holding). Uncommitted work, a PR that closed without merging, a branch nobody opened one for and anything still running are **reported, never removed**. `cc-janitor`'s container, orphan-process and scratch-disk rules — and `quota` — are gone, not folded in here. Preview with `--dry`; what it did is in `~/.cc/state/reconcile.log`.
- **`cc-tmp-reap`** rides the same tick (`--apply`, before the reconcile): it removes the temp dirs the box's own tools leave in `/tmp` and `~/.cc/tmp` — only names it knows, over 24 h old, that no process holds, a Claude session's scratch once no process names that session, a landing's run root once its cc-land is gone. Anything else in `/tmp` is never touched. Bare `cc-tmp-reap` is the dry run: each entry, its size, the total.
- **`cc-suites`** sends the long test suite to a runner on another machine first, and keeps the box's own runs off a pile-up. Every suite offers itself to the runner `~/.cc/suites/remote` names before it takes a slot here, and goes there whenever it answers free and fit; a suite waiting here reaps, once a minute, any run whose slot holder, log or worktree is gone (`cc-suites reap --dry` lists them). Only a pass from the runner counts, and only for the exact tree it shipped: a red there, a dropped connection or a run past 90 min (`CC_SUITES_SPILL_TIMEOUT`) runs here instead. The runner stays out of its owner's way. It answers busy on battery or above half its cores' load, unfit when a tool the suite needs (bwrap, tmux, …) is missing, runs at nice 19 with idle I/O, stops a suite after 85 min, and takes about one run per 8 cores (its own `~/.cc-suite-runner/slots` overrides that). `cc-suites laptop-setup` prints the one PowerShell script that makes a Windows laptop such a runner and pins the host key it installs there, so run that script again whenever you rerun `laptop-setup`. `cc-suites status` shows what the runner answers, with its cores, load and power.
- `cc rc status|restart` — the always-on box session in window `box`; restarting ends its current conversation, so pick `<box>` again in the app.
- Slack, the phone app and tmux can hold the *same* session at once. Between sessions Claude uses its native `SendMessage` (session name = window name); you don't relay.

## Autonomous work (hands-off)
- `cc claim <repo> <row> --executor subagent|worker` — the worktree and branch a row needs, and an exclusive claim on it, with nothing started: no window, no model, no worker. Give a subagent the path it prints; the brief stays where it always was, in `~/.cc/state/<repo>/<row>/task.md`.
- `cc-task show <repo> <row>` — who holds that row and since when. The claim is the box's, not yours to type: `cc done` ends it, it is refused while another owner's process is still running (except a worker dispatch taking over from a subagent, which is how a repair round gets in). From the moment `cc done` records a PR the row is *delivery-pending* and every ordinary claim is refused until that PR merges or is sent back — new work goes on a new row. A stuck claim is cleared by deleting that row's `delivery.json`. `cc board show` prints the same identity on the row.
- `cc <repo> <track> --go "instruction"` — headless worker: fresh context per iteration, journal at `~/.cc/state/<repo>/<track>/progress.md`, ends with a PR and a phone push. Options: `--loop N` (iterations, default 1) `--budget USD` (per iteration, default 8) `--turns N` (default 80) `--model M` (default `claude-opus-5-5` at medium effort, `--effort` to change it — the dispatcher's call, e.g. `fable[1m]` only where Opus 5.5 at xhigh visibly falls short).
- A `--go` track is one thread in `#<repo>`, not a channel: `--go` opens it (`🧵 <repo>/<track> — <title>`) and the worker's lines, its landing line and anything you say to it live there. Reply in the thread to reach it; a headless or finished track hands your reply to the `<repo>` session with the track named. `cc-slack track-thread <repo>/<track>` prints it.
- A BLOCKED, a stall or two capped iterations with nothing to show stop it and go to the planning seat as a request (`cc-notify --ask`); the seat answers or, if only you can, asks you in `#<repo>`. To answer a BLOCKED by hand: append to `~/.cc/state/<repo>/<track>/task.md`, delete the `STATUS:` line from `progress.md`, then `cc <repo> <track> --go ""` (empty instruction = re-dispatch the task already there). Nothing merges to main without you.
- A planning session does not reach for `--go` first: a fix or a backlog row runs as a subagent in its own worktree, a second subagent reviews the diff, and the session commits, pushes and opens the PR itself (`cc done` only works in a worktree `cc` made). It merges on your 👍, or by itself only where you have granted standing merging. The sequence is in `docs/WORKING.md`. Keep `--go` for a real project, or a big task split into serial pieces.
- `cc <repo> <track> --say "text"` — talk to a running *interactive* session; a headless worker's pane is a shell, so it refuses and points you at task.md. `cc handoff <repo> <track>` — a fresh session starts alongside that track's, reads the journal, asks what it missed, then retires the old one (`cc-handoff --overlap`; `--status` shows one in flight, `--abandon` calls it off). `!handoff` in the session's Slack channel or thread does the same from a phone (owner only). The box runs it for you in two cases: a seat past the rotate line, and a seat whose skills changed since it started (a new or updated SKILL.md under `~/.claude/skills` or the checkout's `.claude/skills`), which is handed off at its first idle moment after a turn, at most `CC_HANDOFF_SKILL_MAX` (2) per 20-minute tick; otherwise hand off when the context is worth two sessions' spend. Every session the box starts is addressed by its own tmux window name, and all three shapes are handed off the same way: `<repo>` for one a person steers, `<repo>@<alias>` for an orchestrator (shown to you the other way round, `<alias>@<repo>`; both spellings are accepted wherever you type an address), `<repo>/<track>` for a track. `cc-handoff --brief <target>` prints, in one packet, what a session taking over would otherwise re-read a call at a time: the last journal entry and the lines after it, the unfinished board, what is landing, the live workers, the open PRs and the open asks. A successor is pointed at it automatically; run it yourself when you want the state of a target in one screen.
- **A headless review's findings must land on disk as they're found, not wait for the CLI's return value.** `claude -p ... --output-format json` hands back only the final message in `.result` — a multi-finding review's earlier findings can be missing from it even though the run finished and got billed. Point the prompt at a findings file and have it append one finding at a time as it works, or run `--output-format stream-json --verbose > log.jsonl` and read every assistant message in the log, not just the last. **Prove the harness once against a stub** — a tiny fixture with a known, small number of planted findings — and confirm the file holds every one of them before spending real budget on the real review.
- **Editing a PR's body or title from a session: PATCH it, don't `gh pr edit`.** `gh pr edit <n> --body-file <f>` can exit 0 and leave the PR unchanged — some repos have a Projects-classic GraphQL deprecation warning that looks harmless and silently drops the edit. Use `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@<f>` and read it back with `gh pr view <n> --json body` before trusting it.
- **One command lands it: `cc-land <repo> <pr-number>`.** Gates, merge, the `#approvals` card edited to `landed ✓`, board, ask ledger, `install.sh`, switching on any unit the change *added*, and restarting only what moved — in that order, one line each. **Your 👍 on the card runs the same sequence**, off the reaction thread, so a merge you approve from your phone deploys itself; nothing depends on a session remembering to type this. A failure that would leave the box wrong (gate, merge, install, unit, restart) stops everything; a failure in the bookkeeping (card, board, ledger) is reported and the rest still runs — exit 3 means "deployed, one of those wants a hand". It never merges on a promise (gates run on the PR's own head, in a throwaway worktree), never gates a PR that is already in, never switches on a unit that is off for a reason, and never restarts the box's tmux server. Re-running is the recovery and is safe. Workers cannot call it — `cc-guard` denies it exactly as it denies `gh pr merge` and `systemctl`.

## Sandbox (`ccbox`) — untrusted or fully unrestricted work
- `ccbox <name>` — Claude with `--dangerously-skip-permissions` in Docker; only `~/dev/<name>` is mounted, at `/workspace/<name>`, and `~/.claude` is the box's own volume (`ccbox-claude-<name>`; a new box gets just the login copied in from the newest existing one), so sessions, memory, history and trust never bleed between projects — the login is the one thing boxes share. Egress is limited to `~/ccbox/allowed-domains` (`--open-egress` lifts it); `-c` = `claude --continue`. Tokens: `~/ccbox/env` — missing → it refuses (`cp env.example env`, chmod 600). `ccbox <control-repo>` is refused: that repo's `core/bin/` is the host's `~/bin`.
- `ccbox ls | stop | rm | shell <name> | logs <name> | build [<name>]`. `ls` shows each box's egress mode; `logs <name>` shows the firewall run — a `WARN: could not resolve …` line means that domain was skipped and is *not* reachable. Inner tmux prefix is `C-a`.
- Options apply when the container is **created**: on a running box `ccbox <name> --open-egress|-c` refuses rather than silently attach — `ccbox stop <name>`, then start it again. A stopped box is recreated from the image, so installed packages and `/tmp` are lost; `/workspace/<name>`, its `~/.claude` volume and `/commandhistory` survive. `ccbox build` after editing `~/ccbox/*`.
- **The kernel fence (`cc-fence`).** A worker or member sandbox is built by bwrap; `cc-fence` is what a launcher will run *inside* the finished namespace to make writes a kernel decision rather than a regex one — Landlock rules that grant write, create, remove, rename, truncate and device ioctls under the task's own paths and nowhere else, plus `no_new_privs`, a new session, closed setup descriptors, and signals and abstract sockets scoped to the sandbox's own children. It refuses to start rather than run weaker than that. `cc-fence probe` says what this kernel supports (Landlock ABI 6 or better is the requirement), `cc-fence selfcheck` runs every attack and its allowed twin. One launcher calls it: `cc-member-v2`, the member task launcher behind `CC_MEMBER_V2=1`, which is off by default and not yet used by a live session.
- Project images: `ccbox build <name>` builds `ccbox-<name>:latest` from `~/dev/<name>/docker/Dockerfile` and `ccbox <name>` picks it up (`--image IMG` overrides). Headless: `ccbox <name> --cmd "..."` runs that command instead of interactive claude; from a terminal it runs in tmux and a shell follows it, without a TTY (a timer, a worker) it runs without tmux — ccbox prints its output and exits with its status, both kept in `ccbox logs <name>`. Images may ship `/usr/local/bin/ccbox-project-init` (runs at start).

## Usage limits and model fallback
- **Claude usage limits are waited out, not failed — by the run that hit one.** A rate-limited run is neither an iteration nor an error: `cc-limit` stamps `~/.cc/state/claude-limit` with the reset time, that run waits and reruns the same iteration, and you get **one** push per episode (`<box> limit` → `#alerts`). **One run's limit is not the box's**: every other loop reads `clear` until a second run hits the same limit, and even a limit two runs hit is dropped once `cc-spend`'s ledger shows two sessions answering the limited model (one line to `#alerts`) — on 2026-09-04 one worker's stamp parked the box for six hours while opus kept answering. A limit outlasting 6 h (`CC_LIMIT_MAX_WAIT`) exits that loop with **8** and pings you. `cc-limit status` by hand; `cc ls` / `cc digest` print `⏳ Claude usage limit until 11:40Z` while one stands over the box.
- **A usage limit on the primary model moves every session to the fallback, and back.** `cc-model.timer` ticks every 60 s and switches when `cc-limit`'s stamp names the primary (`CC_MODEL_PRIMARY`) and two runs have hit that limit, or a live pane shows a fresh `usage limit` line *and* a one-turn probe agrees. Live interactive sessions are retyped to `/model <fallback>` (`CC_MODEL_FALLBACK`); headless workers pick it up from `cc-model forced` next iteration. With no limit in force it also retypes a session the CLI left on *another id of the primary's own family* — `claude-fable-5` where the box wants `claude-fable-5-1`, which bills cache reads at 4x — at most once per pane per 10 min (`CC_MODEL_RETUNE_GAP`). **Every session is launched naming a model.** `cc-model current` answers in every state — the override, else the next rung when the primary is not this account's to run, else the primary itself — and `cc` and `cc-rc` pass it as `--model`. Until 2026-09-07 it answered only while the box was *off* its primary, so in the normal state nothing named a model and every session inherited the harness default instead. `cc-model forced` is that older question — what moved the box, and nothing while it is on its primary — and only `cc-loop` asks it, so a worker dispatched with no `--model` still runs on `CC_WORKER_MODEL`. **A session running something else is reported, never moved.** Each tick reads `cc-statusline`'s own per-session record (fresh within `CC_MODEL_STATUSLINE_FRESH`, 120 s — a pane may merely *name* a model) and writes one `mismatch` row per session per hour when it is not on the model `current` names; `cc-model status` counts them (`fable — 2 sessions on another model`). It types nothing: another family is an override's, the chain's or the owner's doing, and the same-family retune above stays the only pass that moves a live session. One line per switch (`<box> model` → `#alerts`). It probes the primary after the reset time (at most every 15 min) and restores on the first answer. `cc-model status` → the current model or `<fallback> until 11:40Z`, dated (`until 2026-09-03T12:51Z`) whenever that is not today; override in `~/.cc/state/model-override`, log in `~/.cc/state/model.log`; never two switches within 10 min, and effort stays what `~/.claude/settings.json` says. **A model the account cannot run is not a limit.** A run answered `… requires usage credits` (or `out of usage credits`) is one model this account is not entitled to: no stamp, no wait — `cc-model unavailable` records it in `~/.cc/state/model-unavailable`, the chain and `cc-model current` leave it out (so a dispatch with no `--model` aims past it, override or none), `cc-model status` says so, and the probe that answers as it forgets it.
- **An interactive session the limit interrupts is resumed too.** A headless worker parks and reruns itself; a session sitting at a prompt just prints the limit line and loses the turn it was mid-way through. So whoever sees the line — `cc-reconcile` on its tick over the planning seats, or the run that hit the same limit — has `cc-limit record` write `<pane, window, reset>` to `~/.cc/state/limit-interrupted` and arm a **one-shot** timer at the reset (a transient `systemd-run`, not a new always-on unit). At the reset `cc-limit resume` types one line into each recorded session through `cc-msg` — *usage limit lifted at HH:MM — continue the turn you were on* — and forgets it. One nudge per interruption, ever: a session that came back by itself is skipped, nothing is sent before the reset, and cc-reconcile does not tick a limited pane at all (that tick would meet the same limit). An orch takes no tick, so nothing records its pane on a round: its channel is what notices. `cc-limit record --dry` says what it would take.

## Your asks (`cc-scope`)
- The board is what the box **took on**; the ledger is what **you asked for**. One row per ask, opened when you make it, closed only against evidence (`~/.cc/scope/<repo>.json`).
- Rows are written down, not captured: `cc-scope add <repo> "<what you asked for>"` opens one, and `cc-scope import <repo> <file>` seeds a batch from a file. The same ask twice bumps a counter instead of opening a second row — `⚠ asked 2×`.
- An ask moves **open → claimed → merged → delivered → verified**, or leaves the queue as **declined**. `cc-scope list [<repo>]` is everything not yet settled; `show <repo> <id>` is one in full, with the separate directives a compound ask contains; `claim`/`track`/`note` as it moves.
- **Merged is not delivered.** A merge puts code on a branch; it does not put anything on your screen — the daemon runs the old code until it restarts, the file is not linked until `install.sh` runs. So a PR number no longer closes a row, and no sentence does. A row names its **own check**: a command whose exit code decides. `cc-scope check-cmd <repo> <id> "<cmd>"` gives it one, `deliver <repo> <id>` **runs** it, and only exit 0 delivers. `cc-land` does this for you, last, after the restart.
- **A row with no check is `unverified`, not done** — it stays on the queue and says so (`cc-scope unverified [<repo>]`). Not every ask can be measured by a command; where none can exist, `verify <repo> <id> --evidence "what you looked at"` is you putting your own name on it, and it is refused while a check the row names is red. An honest "nobody checked" is the point.
- **A session may decide NOT to do something you asked** — `decline <repo> <id> --why "…"`. The reason is required and is kept beside the ask: a declined item stops counting as work but never leaves the ledger. An omission leaves an open item, a decision leaves a reason, and nothing silently vanishes between the two.
- **'Done' is measured against it**: `cc done` prints that track's unsettled asks before it opens the PR, `cc-scope check <repo> [--track T]` exits **1** while any remain, and `cc digest` carries one line — *N asks of yours still open*. Bulk load or replay: `cc-scope import <repo> <file>` (6 tab-separated columns, idempotent; your overlay's seed file).

## The board vs the box (`cc-reconcile`)
- `cc-reconcile.timer` runs `cc-reconcile --apply --notify` every 20 min and 5 min after boot. It **fixes what has one right answer** — a track still `running` with no worker anywhere, a `review` whose PR merged, a `merged` whose PR is still open — writing through `cc-board`, so every change lands as a `reconciled: … → …` note on that track. Nothing else is touched: it never deletes, merges or opens anything.
- **What it cannot decide, you hear about** (once a day per finding, `#<repo>` or `#alerts`): a PR closed without merging, a worktree that is gone, a checkpoint that would not commit, a `review` with no PR, a worktree with no board entry. A track that stopped with nothing in its journal is set to `blocked` *and* reported — that one is both. So is a **runaway it ended** (below).
- Alive means: a `claude` in the track's worktree, a `cc-loop <repo> <track>` (alive for hours with no claude while it waits out a usage limit), or a live pane in its tmux window. Any of the three and the board is corrected *towards* running, never away from it; anything the board touched in the last 10 min is left alone (`--grace`).
- **`waiting` is not `running`, and alive is not the test.** A track whose journal's newest line is `STATUS: BLOCKED: <question>` is set to **`waiting`** — a person must answer before anything happens — even with a live process in its worktree, and it is reported for as long as the question stands. That word is the only thing that reaches your NEEDS YOU list. A loop sitting out a usage limit is **held on the clock**: its own row, never yours to act on. A worker between iterations declared nothing and is simply `running`. Nothing is ever read out of journal prose — the session declares, or it does not count.
- By hand: `cc-reconcile [repo …]` reports and changes nothing, `--apply` fixes, `--json` for machines, `snapshot` prints the effective state of every track (`view`: the same as TSV, what `cc ls` and `cc digest` read), `selfcheck` for the decision table. Exit **1** = something needs you. Log: `~/.cc/state/reconcile.log`.
- **One decider** (review rec #7): every unfiltered run writes `~/.cc/state/reconcile.json` — effective state, live presence, who each track waits on and why. `cc digest` and `cc ls` read it instead of guessing, and fall back to the board when it is missing or over an hour old.

## Six events, one wake (`cc-broker`)
- A session pays a **whole turn** for every event that reaches it, and that turn costs the same whether the event is one line or fifty — cache reads are cheap, so the only saving is in *fewer* turns. `cc-broker` is what the machine-made events go through so a burst of them costs one wake: `cc-reconcile`'s board watchdog feeds it today (one `Environment=` line in the unit; the tool wasn't changed).
- **Three classes.** A line asking the session to *choose* something (`needs you`, `landing stopped`, `STATUS: BLOCKED`…) goes straight through, from any source. Everything else is deduped by `(repo, PR, state, decision-needed)` and delivered as **one digest 12 min later** (`CC_BROKER_DEBOUNCE_S`, plus at most one 60 s tick) — or sooner, riding out with the next event that was going to wake the session anyway. A group the session was already told about inside the hour (`CC_BROKER_REPEAT_S`) is the machine repeating itself: it goes to `~/.cc/state/<target>/events.md` and wakes nobody — and the next message the broker does send carries those lines in its body, so nothing depends on that file being opened.
- **Nothing is dropped and nothing is declined.** There is no budget in it. A held event arrives late, never not at all. If the target's session does not hear it, the box's own session is offered it; if the daemon itself is down, it is retried by `cc-broker.timer` every 60 s and, after three tries with nobody taking it, said out loud to you by `cc-notify` — the rung `cc-reconcile` used to ring for the same case.
- **Who gets it.** Every group goes straight to the session — there is no steward tier any more, and a group being run is claimed, so a second flush arriving meanwhile cannot work the same event twice.
- **A message from a person is never delayed** — Slack messages reach the daemon from Slack, not through this door, so they cannot be held here.
- `cc-broker report [--days N]` is the before/after, in turns: events submitted, turns actually woken, turns avoided — measured from the log, not modelled, because before this every event was its own turn. Log: `~/.cc/broker/events.jsonl`.

## A loop that is working carries on — one that is not gets stopped
- **There is no spend cap anywhere** (some jobs are legitimately expensive). What ends a loop is not being dear, it is not producing.
- **The step limit is a checkpoint, not a verdict.** `cc-loop` reaching `--max-iter` with work *committed* in that iteration buys itself another N and carries on, as often as it keeps committing — a board note each time. An iteration that committed nothing stops at the limit as before (exit **6**), and neither a `STATUS: BLOCKED` nor a run of errors is ever carried on.
- **Runaway, from inside the loop** (exit **9**): three iterations *in a row* that show nothing for their money, each judged against this track's own history — committed nothing and left the journal untouched · repeated the previous outcome verbatim with no commit · spent 5× what a committed iteration costs *this* track with no commit for two iterations. One of those is an ordinary hour; three consecutively is a loop going nowhere. It stops itself, the board says `blocked`, and you get one line with the numbers.
- **Context trim, off by default** (`CC_LOOP_TRIM=1` in `~/.cc/config`, or in front of one dispatch; `CC_LOOP_TRIM=0` in front of a dispatch overrides the file — except a member workspace's own tracks, which take the dispatch-line variable only, because `~/.cc/config` is not inside the boundary): the API drops a worker's older tool results before the model reads them — the tool call stays, only its output goes, and the brief, the constraints, the journal and the six newest results are untouched. Off, nothing is sent and the run is the one the loop has always done. Over 30 real iterations it would have cut a median **21%** off the context a turn carries; a live A/B nonetheless cost **41% more**, because clearing moves the prompt-cache boundary and writing that cache costs 12× reading it. It stays off until a week of `cc-loop context-report <session.jsonl>` on real tracks settles it, on **dollars per accepted PR**.
- **Runaway, from outside** — the one `cc-loop` cannot catch is its own: `cc-reconcile` ends an **orphan** (a headless worker with no `cc-loop` above it — nothing will time it out or commit what it writes) on sight, and a **wedged** loop (alive, nothing moved for 3 h, no usage limit to be waiting on) after two runs 20 min apart have both seen it. `--no-stop` reports without ending anything.

## Recurring audit (`cc-audit`) — hands-off, never fixes anything
- `cc-audit.timer` runs `cc-audit auto` daily at 03:30 UTC: the suites and the `main-gate` row, nothing else — quiet to you, not blind to a red `main`. By hand, `cc-audit checks [--dry] [--no-post]` writes the report and replaces the canvas (`--dry` touches nothing, `--no-post` writes the file but skips Slack). The model-read modes (review, weekly, monthly, delete, arch, patterns) came out in shrink M3 (`docs/scaffolding.md`).
- **checks** (no LLM, ~3 min): the suites (`tests/check.sh`, `tests/selftest.sh`, `cc-slack selfcheck`), user units, heartbeat freshness, Slack daemon and its errors since the last report, disk/load, settings drift vs `config/claude-settings.json`, `~/bin` and home-doc symlinks, leftovers and worker spend — one PASS/FAIL line each.
- **The `main-gate` row owns a red baseline.** Whatever the mode, the first failing suite becomes ONE board track `main-gate` (queued) naming the gate and the first line of the failure; an unchanged red leaves it alone, a different failure updates it in place, green closes it, and once somebody starts it, it is an ordinary track. So a session sees main is red *before* it dispatches, instead of every track rediscovering it and disclaiming it.
- **`cc-audit failure <claim>` is the one thing here that still reads a model** — the failures pipeline's investigator (`docs/design-failure-noticing-2026-09-11.md`), and its passes cannot change anything, by construction: `cc-audit` gathers the evidence itself into `~/.cc/state/audit/<date>-<mode>/evidence/` (scrubbed of any `xox…` token), then runs the model with no shell and no MCP: `--setting-sources ''`, `--strict-mcp-config`, only `Read,Grep,Glob,LS`, everything that writes, runs or posts denied by name — including `Monitor`, which reaches a shell and once got through a `Bash`-only deny. `~/.cc/config`, `~/.ssh`, `~/.claude.json` and the credentials file are denied to `Read`/`Grep` too.
- Reports: `~/.cc/state/audit/<date>-checks.md`, log `~/.cc/state/audit/audit.log`. Slack gets **one line**; the full report replaces the `#<box>` canvas.

## Does the box still work? (`cc-evals`)
- `cc-evals run` — the **regression set**: frozen replays of work this box has already landed, each proved on a pinned base snapshot (the probe must FAIL there) as well as on this tree, plus the control-plane properties. Seconds, no spend, red or green — and the nightly audit runs the same set as one more `## suites` gate, so a red eval is the same single `main-gate` row as any other red baseline.
- **The capability set is where a model is graded**, and it costs money, so no nightly gate runs it: `cc-evals run --set capability --show` puts a set of diffs to a model — some that break one of the landing self-review rules, some that break none — and prints its verdict on each. `CC_EVALS_MODEL=claude-sonnet-5 cc-evals run --set capability` asks another model the same questions, which is how a model, prompt or harness change is judged on quality rather than only on price. `list | last | bless <case>` (blessing is the owner's, at a terminal — a capability case has no reference until you type one, and reports red meanwhile). One file per case in `evals/cases/`, answers are salted digests in `~/.cc/evals/refs`, outside every git tree.

## What must be installed (`cc-units`, `cc-settings`)
- `cc-units check` — every core user unit against `config/units.json`, the one list: enabled, active, and for a timer *armed* (active with no next trigger is down). `cc-units list|restart-for <files>` shows the manifest and what a change would need restarted. Adding a timer = its two unit files + one row.
- `cc-settings check` — names exactly which managed Claude hook or deny rule is missing from `~/.claude/settings.json`; your own keys, theme and extra rules are never drift. Both run inside `cc-audit checks`.
- **`cc-settings apply` is yours alone** — at a terminal, not in a session, not in a track worktree. It backs up, adds only missing *hooks*, never touches `permissions`, and prints missing deny rules for you to paste.

## Notifications
- Sessions and loops call `cc-notify "…"` when they finish or need you → **Slack**, routed by what happened: a decision or an escalation @-mentions you, `#alerts` gets the notable, the rest goes to that repo's `-updates` lane. Your phone only rings (**ntfy**, topic from `cc-notify setup`) for a decision, an escalation or `cc-notify test` — and as the last door, when the box has no Slack or Slack refused the message. Daily digest once a day after 11:00 America/Los_Angeles, from cc-reconcile's tick. Log: `~/.cc/notify.log`.
- That key, and every other one, lives in `~/.cc/config`, and `cc-config get|set|unset|list` is the only way in or out of it: the environment wins over the file, writes are locked, and nothing anywhere *sources* it — a value is a string, never code.
- Every boot posts one message (`cc-boot-notify`): time up, whether the last boot ended cleanly or by power loss, and seconds dark. `cc-heartbeat` keeps a 10 s fsync'd stamp; events accumulate in `~/.cc/state/power-events.log` (`cause=clean-reboot` or `cause=power-loss`).

## Slack, two-way (`cc slack`)
How the conversation itself works — channels, threads, marks, who may do what, the free `!` commands and the agent-facing `cc-slack` ones — is `COMMS.md`. Here: the setup and the box-side commands.
- One Slack app ("<box>", Socket Mode: no inbound port, no tunnel). Once: `cc slack setup` prints the 5 steps — create the app from `slack/app-manifest.json`, `cc slack setup --bot xoxb-… --app xapp-… --owner-email you@x`, `cc slack on`, then `cc slack mkchannel <repo>` per project (**private by default**, `--public` opts out; a `#<repo>--<sub>` name inherits `#<repo>`'s people). The bot cannot create the app itself.
- `cc slack status|channels|off|archive <#chan>`. Extra routes: `~/.cc/slack/routes.json`. From the shell, `cc-slack inject <target> "text"` pushes a message the same way; with Slack off the reply lands in `~/.cc/slack/outbox.log`. `cc-notify` posts into `#<repo>` when the title starts with a repo name.
- Sessions pick up their channel when (re)started after `cc slack on` — for the boot session see RUNBOOK. Built on Claude Code *channels* (research preview, loaded with the development flag).
- **Merge PRs with a 👍** — only for a project named in `CC_SELF_LAND_EXCEPT` (`~/.cc/config`); every other project lands its own green PRs by default, and `cc lands <repo>` says which. `cc done` posts `[<repo>] PR #<n>: <title> — <url>` into `#approvals`; react 👍 on that message and the box queues a landing job — the gates run against the PR's own head, and only on green does it merge, install and restart what moved — answering in the thread. One card per PR: whoever gets there second finds the first and posts nothing. Manual post: `cc-slack post-approval [--force] <repo> <n|url>` (`--force` re-posts after a failed merge). A merged PR never gets a card: the landing edits its card to `landed ✓`, and `cc-slack approvals-sweep` (given a turn by cc-reconcile) does the same to any card the landing missed. Needs `reactions:read` + the `reaction_added` event in the manifest (reinstall after changing it).
- **Live dashboard — a web page off `~/.cc/state/home.json`**, which cc-slackd rewrites every 30 s and within 2 s of any event: what needs you, running/idle counts, the backlog, the channels, `cc quick` work, spend, load, the newest `cc-audit checks` verdict and the last boot. There is no Slack App Home tab — the daemon replaces it once at start with a line pointing at the dashboard (`CC_DIGEST_LINK` in `~/.cc/config`, an https URL, is the link it prints).
- `cc quick doing|done "…"` — log work that has no track; the dashboard lists what is in progress (the 🔧 band of `~/.cc/state/home.json`).
- **Voice memos (`cc-voice`).** A recording sent in a channel is transcribed on the box — Whisper `large-v3-turbo`, CPU, nothing uploaded anywhere — and one small model call condenses it into the message you would have typed; the box posts both under your recording and the session answers the condensed text. **Once per box: `cc-voice install`** — it builds `~/.cc/voice/venv` and fetches the weights into `~/.cc/voice/models` (~1.5 GB, nothing system-wide, nothing apt). `cc-voice status` says whether it is ready, `cc-voice transcript <file>` transcribes anything on disk without a model call. Measured here: ~45 s and 2.1 GB RSS for a short memo, nearly all of it loading the model, which is freed again after each one. Until it is installed — and in a parked project, which transcribes nothing — a memo stays a plain attachment: the message still arrives and its line names `cc-voice text <path>` as what reads the recording.
- **24 h of vitals (`cc-vitals`).** `cc-vitals show` draws the last day of CPU, RAM, load, temperature, power and disk as one chart — every series a percentage of its own capacity on a single 0-100 axis, the legend carrying the real numbers. `cc-vitals record` is the recorder behind it (one row a minute: counters by delta, gauges by mean-and-max) and it is installed OFF (`enable: owner` in units.json — `systemctl --user enable --now cc-vitals.timer` switches it on) — a day of history sits in `~/.cc/state/vitals/`. `cc-vitals render` redraws `current.png` (matplotlib, headless Agg) and `current.txt` (block-glyph, always available as the fallback); `--if-stale` keeps it from redrawing a 24 h chart every minute.
- **Both graphs in a browser (`cc-graphs`).** `cc-graphs serve` puts token spend over time and the same cc-vitals series on `http://127.0.0.1:5190/`, interactive: pick the window, the metric (tokens, output tokens, or the dollar estimate) and what a line is — lane, track, repo, model or kind. Also `cc-graphs stop|status`, `--port`, `--foreground`, and `cc-graphs tokens --by track` for the same series as JSON. It binds loopback and answers GET only, and it never exposes itself: one `tailscale serve` line does that and it is the owner's to run. What a line on the token graph means, and what it leaves out, is the header of `core/bin/cc-graphs`.

## E-mail (`cc-mail`)
- The box has a mail address of its own. A mail it receives gets a mirror thread in Slack, and a reply there goes back as mail by itself; a mail the box starts is one JSON file (`to`, `subject`, `body`, `attachments`) handed to `cc-mail send --json FILE`, only to an address you have verified (`MAIL_SEND_ALLOW`); a named file is attached or the mail is not sent and the line says which and why. Every session kind is told this at start (`config/mail-prompt.md`), so any channel can be asked for a mail. Setup and the wire: `cc-mail --help`.
