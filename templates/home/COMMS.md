# <box> — Talking to your projects and agents

Shallow first: the six moves, then who is who, then each channel in detail. Source of truth: `~/dev/<control-repo>/home/COMMS.md`.

## The six moves
1. **Slack `#<repo>`** — ask, instruct, get the answer in a thread. Phone-first. The repo's planning session answers; if none is running it is started for you.
2. **DM the bot** (or `#box`) — the box itself: status, start things, ops questions, "what's running?".
3. **Phone app → Code → session** — Remote Control: the *same* session, but you see its screen, can stop it, and type when Slack is the wrong shape (long pastes, approvals).
4. **Laptop: `ssh` + `cc <repo>`** — the same session again, in tmux. Everything you say in Slack, the app or the terminal lands in one conversation per project.
5. **Hands-off work** — in `#<repo>`: "dispatch a worker on track *name* to do *X*", or on the box `cc <repo> <track> --go "X"`. It runs headless on its own branch, ends with a PR and a ping in `#<repo>`. Nothing merges without you.
6. **Dashboard — tap the bot in the sidebar → *Home*** — one live view of the whole box, refreshed the instant you open it, every second for the first minute, within ~2 s of any event, otherwise every 30 s and never posted as a message: units 🟢/🔴, every channel with its session and its open ❓, every track with iteration/cost/PR (🏃 = a worker is running), the last audit verdict and boot. Read-only; `!status` `!threads` `!digest` say the same in text.

## Who is who
| Agent | Where it lives | Reach it | Does |
|---|---|---|---|
| **box** session | tmux `main:box`, `~/dev`, Remote-Control name `<box>` | DM the bot · `#box` · phone app "<box>" · `cc` then window `box` | ops, status, starting/stopping things, questions about the box |
| **`<repo>` planning session** | tmux window `<repo>`, `~/dev/<repo>` on the default branch | `#<repo>` · phone app `<repo>` · `cc <repo>` | plans, dispatches tracks, reviews PRs; never merges, never auto-commits |
| **`<repo>/<track>` session** | window `<repo>/<track>`, own worktree + branch `track/<track>` | `#<repo>--<track>` · phone app `<repo>/<track>` · `cc <repo> <track>` | does one unit of work; every turn is auto-committed and pushed |
| **headless worker** (`--go`) | same worktree, no chat, fresh context per iteration | `cc <repo> <track>` shows its window; log `~/.cc/state/<repo>/<track>/loop.log` | executes a task file; `STATUS: DONE` → PR; `STATUS: BLOCKED` → pings you |

Sessions are named after what they own, so the Slack channel, the phone-app entry and the tmux window all share the name. (Claude.ai / Claude Desktop check in through the owner's **Slack** connector.)

## Slack in detail
- **Channels are projects.** `#<repo>` ↔ `~/dev/<repo>`; `#<repo>--<track>` ↔ that track; DM or `#box` ↔ the box. Anything else: name a channel after a folder in `~/dev`, or map it in `~/.cc/slack/routes.json` (`{"#ops": "box"}`). `cc slack mkchannel <repo>` creates + wires a channel — **private by default** (`--public` opts out), and a `#<repo>--<sub>` name starts with `#<repo>`'s people already in it. A channel that is already public stays public: no bot API converts one (Slack's `admin.conversations.convertToPrivate` is Enterprise Grid only), so `cc slack channels` flags each one and you flip it in Slack (channel → Settings → Change to private). In a public channel *anyone in the workspace* can reach that session.
- **Every channel is a session.** A channel the bot is in that maps to nothing else *becomes* one: on its **first message** (never in advance, never on channel creation) the box creates `~/dev/<channel name>` — normalised to lower-case `[a-z0-9-]` — with a `CLAUDE.md`, the marker `.cc/member-facing` and a git repo, starts the session there and answers `starting a session for #<name> — its dir is ~/dev/<name>`. Such a session is **member-facing by default** (`cc-guard` gates it from its first tool call) and **read-only outside its own directory**: anything that needs a change comes to you, in the thread and via `cc-notify`. Bounded at **3 new dirs an hour**, so a channel-creation spree cannot spawn sessions without limit — past that you get one line asking you to create the dir by hand. Never for DMs (yours alone), `#approvals`/`#alerts` (not sessions), an archived sub-orch channel, or a name that normalises to nothing. `cc slack channels` marks the auto-provisioned ones and `cc slack status` states the policy. **Promoting one to a real project is yours to do:** move or rename `~/dev/<name>`, add a git remote, and drop `.cc/member-facing` once the work is no longer member-facing.
- **A track channel whose worker is headless.** `#<repo>--<track>` while a `--go` worker owns that worktree cannot chat, and no second session is ever started on it. Your question goes to the **`<repo>` session** instead, prefixed `[asked in #<repo>--<track> while its headless worker runs]` — it answers you in that channel, and one line there says so. The worker is untouched.
- **Peer orchestrators.** `cc <repo> --orch <alias>` starts a peer session in the same channel for long/vague work; hand it a thread by starting your message with `@<alias>` (e.g. `@ai-dev take this`), and bring the main session back with `@main`.
- **Sessions can @-mention people.** A session writes `@handle` and Slack posts a real mention that notifies that person — the handle is the one it read in their own message (`@ada.byron`), but a **display or real name, or just a first name** (`@ada`), works too: the members of **that channel** are tried first, so one Ada in the channel resolves even when the workspace has three, and only then the workspace-wide table. Two people in the channel answering to the same form leaves it as plain text (a wrong id pings the wrong human) and the daemon logs the token it could not resolve. A mention only notifies someone **already in that channel** (the bot never invites anyone, so add them yourself), and `@main` / `@<alias>` still mean a hand-off to a session, not a person.
- **Sub-orchs get their own channel.** Starting one (`cc <repo> --orch <alias> "brief"`) also creates `#<parent channel>-<alias>-<id>` (4-char id; an orch spawned by an orch nests: `#<repo>-<parent alias>-<alias>-<newid>`), invites you, puts the brief in the channel purpose and posts one line in the thread that asked for it — `🤖 @<alias> has its own channel: #…`. In there you need no `@`: every message is that orch's, while `@main` / `@<other>` still hands a thread over and `@<alias>` in `#<repo>` keeps working. Marks, nudges, 🏁 and 🔧 behave as in any channel. It is **archived** when the orch exits (`cc slack archive <#chan>` does it by hand, and a daily janitor archives one whose orch has been gone 24 h); archived channels neither route nor show on Home, where sub channels sit indented under their parent (`    ↳ #…`).
- **Threads are conversations.** The session replies in a thread under your message; continue there. A new top-level message is a new topic — the session keeps its own memory either way.
- **Reactions tell you the state.** A thread root carries TWO marks at once — *whose turn it is* and *what the session is doing*. Turn: ❓ = it needs you · 🔴 = the session owes you an answer · 🟠 = handled, nothing for you to do · no mark = you closed it, or it went quiet. Work: 🔧 = still on it · ✅ = finished (the session sets both; the bot also adds a 🔧 by itself while a session is mid-turn). So 🔧🔴 = working *and* owes you a word; while a 🔧 stands a thread never ages into ❓; ✅ stands alone. On your own messages: 👀 = the session has it (it comes off when it answers) · any other reaction *from the session* (👍 yes · 👎 no · ✅ done · ❌ can't · 🤔 unclear) is its answer when no words were needed, and the thread turns 🟠 · ✅/❌ = your `yes <id>`/`no <id>` was delivered · "⏳ starting…" = the session had to be started (your message is queued and lands once it's up).
 The 🔧 also appears by itself while the session is mid-turn on that thread (≈30 s lag) and leaves ≈1 min after it goes idle; finished board tracks drop off Home unless their PR waits for you.\n- **Your 🏁 closes a thread; your 👍 answers it.** A 🏁 on *any* message of a thread takes every mark off its root and stops its nudges. Reply there again and the thread re-opens with its normal mark (the bot cannot remove your reaction, so the old 🏁 stays visible and is ignored from then on; flag times survive restarts in `~/.cc/slack/flags.json`). Every other reaction you put on one of the *session's* messages is delivered to it as `👍 on your 07:12 reply: "…"` — 👍 means confirmation ("act, don't ask again"), 👎 means no, anything else arrives as itself. Only a session that is already running hears it (a reaction never starts one), and a channel member's reactions do all of this exactly as yours do — see *Who can talk*. Two things a 🏁 does *not* do: it never stops the work — the session carries on and keeps answering in that thread, the flag only quiets your side — and it never speaks for the session. When your question only needs a yes or a no, the session answers you the same way, with a reaction on your own message (👍 yes · 👎 no · ✅ done · ❌ can't · 🤔 unclear, then it asks); its 👀 comes off, the thread goes 🟠 and nothing nudges you.
- **Free commands** (no tokens spent): `!status` live sessions + board · `!digest` all tracks with PR state and cost · `!sessions` who is subscribed (`<box> [main]`, `<box>@ai-dev`) · `!start` start this channel's session · `!say <text>` type into a session that has no channel (answer stays in its terminal) · `!restart box|<repo>[/track]|slack|tmux` recover a wedged session or the Slack daemon itself, no live session needed (`!restart tmux` needs a confirm — see RUNBOOK) · `!reboot` reboot the whole box (needs `!reboot confirm` — see RUNBOOK) · `!threads` on-demand snapshot of this channel's open threads in three lists — *needs you* (❓), *with the session* (🔴) and *handled* (🟠); 🏁 a thread to hide it · `!box` health · `!ping` · `!help`.
- **Open threads nudge themselves.** Every 15 min, any ❓ thread that has needed you for over 30 min gets one reminder posted in-thread, never repeated, carrying the actual ask (a thread you have 🏁'd is never nudged): `❓ still waiting for you (33m): <the question>`, or `⏳ no answer for 33m — !restart <target> if the session is wedged` when it is the session that has gone quiet. `!threads` is the same state pulled on demand.
- **Threads carry their own status.** The bot recomputes one mark per thread root from the thread itself — no bookkeeping, nothing to maintain: ❓ = *you* must act (the session asked you something — a 🔐 permission prompt, `STATUS: BLOCKED`, a question — or your own last word has gone 30 min unanswered, i.e. a stalled session: `!restart <target>`) · 🔴 = the session owes you and is still inside its 30 min, after which the ❓ takes over · 🟠 = it answered and asked nothing, so there is only reading to do; that mark disappears once the thread has been quiet for 48 h. So a channel with no ❓ has nothing waiting on you. Marks appear within ~45 s of what caused them (a 🔐 prompt and your own messages mark instantly) and change on their own — 🏁 is the only reaction you ever need to set.
- **Agent parity on the box** (`cc-slack <cmd>`, owner/session use only, not Slack commands): `history`/`thread` pull compact recent messages (small n by design — an information diet, not a dump) · `edit`/`unsay` fix or remove the bot's own posts (including the signed `<box> · <session>` ones) · `pin`/`unpin` · `canvas` replaces a channel's canvas from stdin markdown. Sessions get the same via MCP tools; posts show as `<box> · <session>` (customized display name).
- **Approvals.** When a session hits a permission prompt you get `🔐 … Reply "yes abcde" or "no abcde"` in the channel. Answer there or in the terminal — first answer wins. Owner gates (merge, deploy, destructive/host changes, external comms) are hard-blocked for autonomous sessions and *asked* for interactive ones; from Slack you are the one who says yes.
- **PR merges.** Every finished track's PR lands in `#approvals` as `[<repo>] PR #<n>: <title> — <url>`. React 👍 and the box squash-merges it (remote branch deleted); the outcome comes back in the thread (✅ merged / ❌ with gh's error / "already merged"). Anyone else's 👍, or a 👍 on anything but the bot's own PR post, is ignored. A **failed** merge no longer stops in that thread (nothing routes there): it also pushes to your phone as `[<repo>] PR #<n> merge failed`, posts in `#<repo>` (not the fallback channel) and is injected into the repo's session, so an agent picks up the fix.
- **Attachments.** Photos, screenshots and files you send are downloaded to `~/.cc/slack/files/` and the session reads them (images render).
- **Shared messages.** Forward or share a message to a channel with the bot and the session gets its content as one bracketed line — `[shared message from #help by ada at 2026-08-30 05:33Z: …]` — even when your own text is nothing but the mention (Slack keeps the shared content in `attachments`, not in the text). Capped, and Slack's own link previews are not folded in.
- **Who can talk:** **anyone who can post in a channel that routes to a session.** Slack channel membership *is* the access control — you curate it as workspace admin, and whoever is in the channel is answered exactly as you are (the session sees `role="member"` instead of `role="owner"` in its tag). What a member **cannot** do: authorize an owner gate (merge to main, deploy, spend over budget, destructive or host/network/service changes, external comms in your name), answer a `🔐` permission prompt (❌ + one line), run any `!` command beyond `!help`/`!status`, or hand a thread over with `@<alias>` — the session helps them with the rest and asks *you* for the gated part.
- **Reactions from anyone in the channel count as yours** (since 2026-08-30). A member's :+1: on a PR post in `#approvals` squash-merges it, their 🏁 closes a thread, and any other reaction of theirs on a session's message reaches it as a verdict tagged with their name and `role="member"` — so the session can weigh a colleague's 👍 against yours. The reasoning: you curate who is in each channel and you do not put members in sensitive ones, so **membership is the approval gate**. Two things stay yours alone: reactions in a **DM** (nothing gates a DM, and it reaches the box session), and **permission answers** — `yes <id>` is authorization, not a verdict, and only you give it. When a member asks for something the box gates on you, the session does the ungated part, says which part needs you, and **@-mentions you in that thread**.
- **A member-facing session is gated by code, not by its CLAUDE.md.** Put the marker file `.cc/member-facing` in the folder (`~/dev/<repo>/.cc/member-facing`) and `cc-guard` treats *every* session started there as role=member: on top of the owner gates (merge/deploy, host/service/destructive changes, external comms in your name, edits outside that folder) it refuses to **dispatch work** (`cc … --go`, `cc-loop`, a headless `claude -p`), to **read the box's secrets** (`~/.cc/config`, `~/.ssh`, `~/.claude/settings.json` — by shell command *and* by file-reading tool) and to **re-wire Slack** (`cc slack` off/setup/mkchannel/archive). `cc-notify` stays open, so the session can always ask you. The marker is the trigger — no env var, no config — so it holds for its subagents and for a session you start by hand, and only you can lift a gate, one call at a time. **Honest ceiling:** those command gates are a blocklist, not a sandbox — they stop accidents and casual prompt-injection, not a determined attacker; for real isolation run that session in `ccbox`.
- **DMs are yours alone.** A DM reaches the box session — the most privileged target — and no channel gates it, so a non-owner DM gets 👋 and one line ("not paired with this box — ask the owner to add you to the project's channel"), never a session. Your Slack login is still part of the box's security; the channel member list is now the rest of it.
- **What arrives on its own:** `cc-notify` posts into `#<repo>` (worker done / blocked / stalled, PR links), boot notices and the daily digest into `#<box>` or `SLACK_CHANNEL`, plus ntfy pushes to the phone.
- **If the primary model hits its limit the box moves to the fallback and back — one line in `#alerts` each time** (`<box> model`): every live session is retuned in place and new ones start on the fallback, until the primary model answers a probe again (`cc-model status`).
- **The audit is one line, never a wall of text:** `cc-audit` (03:30 UTC — **review every 3rd day**, weekly on Sundays, monthly on the 1st) posts a single line into `#<box>` and puts the whole report on the **`#<box>` canvas**. The review's line is its verdict on *your* experience (`… · 3 improvements → canvas`); the code audits' is `OK: 0 checks failed · 1/5 findings · canvas updated`. Monthly findings also land on the board as `audit-<yyyymm>`; nothing gets fixed until you say so.
- **The review is the one that reads you, not the code:** every third day it goes through your channels and threads, the boards and journals, and reports how long you waited for replies, where a message ignored your style rule (quoting it), what burned budget without a result, and **what you had to do by hand that should have been automatic**.
- **Long tasks:** the session sends a one-line ack, works, then posts the result. **Messages are structured, not long** — a few section bullets with sub-bullets for detail (generally few, no hard cap when the content needs it); reference material lands where it belongs, linked in one line: the channel's *canvas* (living project state, replaced in place — open it from the channel header), the repo's `docs/` (lasting reports, on GitHub), the track journal (running detail). If you want to watch, open the same session in the phone app.
- **Nothing answers?** `!ping` (daemon alive?) → `cc slack status` on the box → `journalctl --user -u cc-slackd -n 30`. A session started before `cc slack on` has no channel: restart it and message again — `cc handoff <repo> <track>` for a track (it needs both), `cc rc restart` for the box session, and for a planning session close its window (`tmux kill-window -t main:<repo>`) then `cc <repo>`.

- **Files from the box.** `cc-slack post --file <path> [--to #<repo>|C…|U…] [--thread <ts>] [--title <t>] [-m <text>]` uploads a file as the bot — default target is your DM, `--thread <ts>` puts it in a thread (the box uses it for guides, PDFs, screenshots). Pure Web API (no daemon needed); clear errors on `missing_scope` / `not_in_channel`. **A session sends its own files** the same way, with the `file` MCP tool: when the answer *is* a render, a chart or a screenshot it attaches the image in the thread that asked, instead of describing it. It may only read from its own folder, `/tmp` or `~/.cc/slack/files` (never `~/.cc/config`), 25 MB max — and if there is no token it tells the session the file was logged, not sent.

## Claude Code sessions (phone app or terminal)
- `cc` attach tmux · `cc <repo>` planning session · `cc <repo> <track>` track session · `cc resume` menu · `cc ls` / `cc digest` what's live and where things stand.
- Reconnect = the same command; sessions survive disconnects and reboots (tmux `main` is a user service). `cc -c <repo>` only if a process died.
- Nudge a running session: `cc <repo> <track> --say "text"` (types into it) · `cc handoff <repo> <track>` (journal + fresh context) · `cc done <repo> <track>` (PR) · `cc rm` (remove a track).
- Between sessions, Claude uses its native `SendMessage` (session name = window name); you don't need to relay.
- Phone app: Code → the session name. Remote Control shows the live screen; Slack and the app can be used on the same session at the same time.
- Box session: `cc rc status|restart`. Restarting ends its current conversation (pick `<box>` again in the app).

## Hands-off work and what needs you
- `cc <repo> <track> --go "task" [--loop N] [--budget USD] [--model sonnet]` — fresh context per iteration, journal at `~/.cc/state/<repo>/<track>/progress.md`, capped by budget and turns, ends in a PR + a ping. Or say it in `#<repo>` and the planning session runs it.
- It stops and pings you when **BLOCKED** (answer: edit the task file, rerun) or stalled. Answer questions in `#<repo>`; the planning session can also re-dispatch.
- **You decide:** merges to main, deploys, spend beyond budgets, anything destructive or host/network-level, messages sent in your name. Everything else the agents do on their own.
